## 零、威胁模型与预期（先说清楚挡什么、不挡什么）

> 所有者原话（2026-11-04）：「我这只是为了挡一些**技术水平不高**的恶意用户。
> 要是有人**花钱雇人**去刷流量，就算是大网站都不一定扛得住，何况我这个小小网站呢？」

### 0.1 本方案挡的是谁

```
✅ 拿现成工具扫接口的（sqlmap / 爬虫框架 / 爆破脚本）
✅ 手写几行 requests 就想刷的
✅ 清 Cookie 换身份、反复重试的低成本投机者
✅ 一个脚本把队列塞满、把 CPU 吃光的"顺手作恶"
```

### 0.2 本方案**不**挡谁（要认清）

```
❌ 花钱雇人 / 买僵尸网络 / 打码平台流水线
❌ 有预算的定向攻击（分布式 IP、真人众包、GPU 算力）
❌ 链路层/带宽层攻击（那是 DDoS 防护/CDN 的事，要花钱，本方案不涉及）
```

**原因很朴素**：一切应用层手段都是在"提高单次请求的成本"，
而对方愿意为单次请求付钱时，这个成本差就被抹平了。大站也一样。

### 0.3 所以设计目标是这四条（不是"防住所有攻击"）

```
① 让**技术水平不高**的人刷不动（成本 >> 收益）
② 让**正常用户完全感觉不到**（不误伤，这是小站最怕的）
③ 出事时**能定位**（谁在刷、刷什么、从哪来）
④ 出事时**能快速止血**（下面 0.4 的保命顺序）
```

### 0.4 真被打时的"保命顺序"（比限流更重要）

```
第 1 优先：数据不丢
  ⇒ 备份是每天 04:00 的，被打时不要动数据库；必要时先停写入口

第 2 优先：站点活着（哪怕降级）
  ⇒ 维护模式：全站只读 / 只允许已登录用户 / 关闭解析与搜索
  ⇒ 静态页由 nginx 直接发，后端不参与 ⇒ 打得再狠也能打开一个"正在维护"页

第 3 优先：止血
  ⇒ 短封 + 关掉最贵的入口（解析、搜索、导出）

最后才是：花钱上 CDN / 清洗 / 换 IP
```

✅ **保命开关已实现（2026-11-04）**，两个入口等价：

```
后台  「站点参数」页顶部「站点保护模式」卡片 → 打开/关闭按钮（会留痕）
SSH   deploy/maintenance.sh on|off|status（admin 登不进来时用这个）
```

```
打开后：已登录 admin 一切正常（要能进来解除）；未登录只能只读浏览；
        搜索 / 登录（非 staff）/ 写操作 一律 503；解析队列暂停领取新作业
状态存放：data/uploads/.runtime/maintenance.flag（文件，不依赖 DB/Redis）
判定位置：web/middleware.ProtectModeMiddleware（先查 staff，再判只读/搜索）
⚠ 登录闸门放在 `authenticate()` **之前**：否则攻击者仍能用登录触发 PBKDF2，
   等于拿你的 CPU 当放大器
```

### 0.5 一句话

```
限流是"防小偷的门锁"，不是"防军队的城墙"。
门锁值得装（成本低、误伤小、挡住了绝大多数情况）；
城墙不要自己修（修不起，也不是这个站该操心的事）。
```

## 一、结论摘要（先看这段）

```
① 现在有 5 套限流/封禁机制，但其中 2 套**实际失效**：
   · 设备令牌发牌配额  → 退化成"全站 150/小时"（已实测打满）
   · IP 封禁          → 所有请求 IP 塌成网关，is_bannable 拒绝封它 ⇒ 完全无效
② 登录完全没有"失败次数"限制（只有审计记录）
③ 只有搜索接口被限流，写操作（发布/导出/删除）没有任何频率保护
④ 根本原因是**拿不到真实客户端 IP**；等自建隧道就绪后这些才能修对
⑤ 本方案不引入任何第三方服务（隐私优先），验证码**自己画**（Pillow）
⑥ 处置是层层递进的：429 → 蜜罐 → PoW → 图片验证码 → 短封（见第四、八、九节）
⑦ ⚠ **本方案只挡"技术水平不高的恶意用户"，不抗花钱雇人刷流量 / DDoS**（见第零节）
```

## 二、现状盘点（实测，不是推测）

### 2.1 五套机制

| # | 机制 | 代码位置 | 识别身份 | 阈值 | 生效范围 | 失败行为 |
|---|---|---|---|---|---|---|
| M1 | 设备令牌发牌 | `core/device.py` | **IP** | 150 / 小时 | 只影响"发新令牌" | 放行 |
| M2 | 搜索限流 | `web/ratelimit.py` + `search/terms.allow` | `u<id>` / `d<token>` / `anon` | 10 次/秒/人；`anon` 90 次/秒**全体共享** | 仅 `GET /api/*` 且带 `q` | 放行 |
| M3 | IP 封禁 | `core/access_audit.py` + `web/middleware.py` | **IP** | 手动（临时/永久） | 全站每请求（403） | — |
| M4 | 业务配额 | `core/quota.py` | 用户 | 3 次/天 · 8 次/周 · 3 个项目 | 提交审核 | 拦截 |
| M5 | 队列上限 | `jobs/dispatch.py` | 用户 + 全局 | 全局 50 · 单人 3 | 解析作业 | 拒绝（429） |

```
nginx：limit_req / limit_conn = **0 条**（2026-11-02 撤除，原因见 2.3）
```

### 2.2 两个失效点（有实测证据）

**① M1 事实上是"全站 150/小时"**

```
所有外部请求在 nginx 眼里都是同一个地址（宿主机 / 隧道那头）
⇒ "每 IP 150 张/小时" 变成 "全站 150 张/小时"

实测（2026-11-03）：
  astrolabe:dev:issue:127.0.0.1:498264 = 222   ← 已超过 150
  ⇒ 该小时内**新访客拿不到令牌**，全部落进 anon 共享桶（90 次/秒，所有人共用）
```

**② M3（IP 封禁）当前完全无效**

```
client_ip() 取 X-Real-IP = nginx 的 $remote_addr = 网关地址
is_bannable() 明确拒绝封 127.0.0.1 / 内网段（防自锁）
⇒ 后台「封禁」按钮点了不生效 —— 安全但无用
```

### 2.3 为什么 nginx 的限流被撤掉

```
撤除前：limit_conn / limit_req 按 $binary_remote_addr
但该地址是网关 ⇒ 实际是"全站总闸门"
表现：一个人刷，所有人一起被限（误伤式）
⇒ 撤除，把限速交给应用层按身份做（M2）
⇒ 等真实 IP 可用后，nginx 限流才有意义（见第十二节）
```

### 2.4 缺口

| 缺口 | 现状 | 严重度 |
|---|---|---|
| 登录无失败计数 | 只有 `login_fail` 审计，无锁定/延迟 | **高** |
| 写操作无限流 | 发布/导出/删除只有业务配额（3 次/天） | 中 |
| `anon` 桶全局共享 | 一个脚本占满，所有未登录用户受影响 | 中 |
| 固定窗口边界效应 | 第 59.9 秒 + 第 60.1 秒可各放一轮 | 低 |
| fail-open | Redis 故障时 M1/M2 全部放行（设计取舍） | 低 |

## 三、设计原则（借鉴大公司做法）

| 原则 | 含义 | 本方案的体现 |
|---|---|---|
| **① 身份优先，IP 兜底** | 有账号按账号算；IP 只用于匿名 | 登录用户完全不占 IP 额度 |
| **② 分层响应，不一步到位** | 429 → 蜜罐 → PoW → 图片验证码 → 短封，**不做永久封** | 第四 / 八 / 九节 |
| **③ 认证类数"失败"不数"频率"** | 限的是试错次数，不是访问次数 | 登录/注册 |
| **④ 按端点定政策** | 贵的接口严，便宜的不限 | 搜索/导出严，列表宽，静态不限 |
| **⑤ 挑战代替拒绝** | 可疑时要求"证明是真人"，而不是拉黑 | PoW（第八节）+ 图片验证码（第九节） |
| **⑥ 零第三方** | 访问者数据不出服务器 | 不用 Turnstile / reCAPTCHA |

> 为什么不用第三方验证：小站无法承担"用户 IP 与行为交给第三方"的隐私与合规风险。

## 四、目标架构（四层）

```
┌─ 第 0 层：静态资源 ────────────────────────────────┐
│  /app/*、/static/*   nginx 直接发，**不限流**       │
└────────────────────────────────────────────────────┘
┌─ 第 1 层：边缘（nginx，需要真实 IP）───────────────┐
│  连接数 / 请求速率  超限 → 429（不封）              │
└────────────────────────────────────────────────────┘
┌─ 第 2 层：身份（Django 中间件）────────────────────┐
│  按 u<id> / IP 分桶；搜索、写操作、导出各有额度     │
│  超限 → 429 + Retry-After；反复超限 → 要求 PoW      │
└────────────────────────────────────────────────────┘
┌─ 第 3 层：业务（视图/领域层）──────────────────────┐
│  配额（3 次/天、3 个项目）、队列（50 / 3）          │
└────────────────────────────────────────────────────┘
```

**一句话：nginx 挡"不是人的流量"，应用挡"是人但太快的"，配额挡"规则上限"。**

## 五、参数表（★ 标记处需所有者拍板）

### 5.1 读接口

| 接口 | 身份 | 额度 | 超限动作 |
|---|---|---|---|
| 静态资源 | — | 不限 | — |
| 列表 / 详情（普通读） | 登录 `u<id>` | ★ 30 次/秒 | 429（1 秒后恢复） |
| | 匿名 按 IP | ★ 10 次/秒 | 429 |
| **搜索**（带 `q`） | 登录 `u<id>` | 保持 10 次/秒 | 429 |
| | 匿名 按 IP | ★ 5 次/秒 | 429 → 反复则 PoW |

### 5.2 写接口

| 接口 | 身份 | 额度 |
|---|---|---|
| 发布 / 删除 / 修改 | `u<id>` | ★ 30 次/分钟 |
| 导出（`500 篇上限` 那个） | `u<id>` | ★ 5 次/分钟 |
| 提交解析 | `u<id>` | 保持 M4/M5（3 次/天、队列 3） |

### 5.3 认证接口（只数失败，不数频率）

| 维度 | 阈值 | 处置 |
|---|---|---|
| 同一**用户名**失败 | ★ 5 次 / 15 分钟 | 延迟 2 秒；第 6 次起锁 15 分钟 |
| 同一 **IP** 失败 | ★ 20 次 / 15 分钟 | 该 IP 的登录请求要 PoW |
| 注册 | ★ 3 次 / 小时 / IP | 429 |
| 成功登录 | — | **清零**（正常用户永远碰不到） |

### 5.4 封禁（人工，短封为主）

| 情形 | 时长 | 说明 |
|---|---|---|
| 首次确认滥用 | ★ 5 分钟 | 自动过期 |
| 同 IP 反复 | ★ 30 分钟 → 24 小时 | 递进 |
| 住宅 IP 上限 | ★ **24 小时** | 绝不能永久封（可能是一整个小区） |
| 机房 / 云 IP | 可 7 天 | 那里一般不是真人 |
| 登录用户 | 走**账号**处置 | 不动 IP |

## 六、身份体系与"设备令牌"的去留

### 6.1 现有三层身份

| 身份 | 载体 | 可信度 | 用途 |
|---|---|---|---|
| `u<id>` | Django session（7 天，HttpOnly） | 高 | 权限 / 配额 / 限流 |
| `d<token>` | `at_device` cookie（180 天，HMAC 自验证） | **低**（清 Cookie 即换） | 仅限流 |
| `anon` | 无 cookie | — | 全体共享桶 |

### 6.2 令牌的处置（★ 需拍板）

**方案 A：删掉 —— ✅ 已于 2026-11-04 执行**

```
删除内容：core/device.py 的令牌实现（只留 client_ip）、DeviceTokenMiddleware、
          settings 里的注册、access_audit 的 device_issue、后台「设备令牌发放」tab
限流身份：u<id> / a<ip>（匿名按真实 IP）
⚠ 删的时候把"IP 封禁拦截"一起删掉了（它原本写在 DeviceTokenMiddleware 里）
  ⇒ 冒烟脚本当场抓到「被封 IP ⇒ 403」失败，已拆成独立的 BanCheckMiddleware
```

（原描述如下，保留作为决策记录）

```
匿名一律按真实 IP 计账
优点：少一层中间件、少一个 180 天持久标识、少一个已爆的配额雷
缺点：同一出口的多人共用额度（靠"额度按家庭定"缓解）
```

**方案 B：保留但降级**

```
不再做"发牌配额"（那个 150/小时 直接删）
只保留：① PoW 通过后记名 10 分钟  ② 带令牌的匿名额度略高
⇒ 清 Cookie 对攻击者不利（掉回更低额度），对正常人无影响
```

> **建议 A**：你的量级（日活几百）用不上分账；B 的成本在于多维护一套 cookie 语义。
> 若选 A，`web/middleware.py::DeviceTokenMiddleware`、`core/device.py` 的发牌部分、`device_issue` 审计一并移除。

## 七、匿名按 IP 的误伤，三个缓解

```
① 登录用户**不占** IP 额度
   一个小区 50 人，登录 40 个 ⇒ 匿名额度只被剩下 10 人消耗

② 额度按"一家/一办公室"的量级定
   搜索 5 次/秒：正常人 1 秒点不到 2 次 ⇒ 一家三口共用也够

③ 超限先 429，反复超限才要 PoW
   真人最多多花 1 秒；脚本要付算力
```

## 八、PoW（工作量证明）设计

### 8.1 原理

```
服务端给随机 challenge
客户端找 nonce，使 SHA256(challenge + nonce) 前 N 位为 0
平均需要 2^N 次哈希（客户端）；验证只需 1 次（服务端）
```

### 8.2 难度与耗时

| 难度 N | 平均哈希次数 | 桌面 (~200 万/秒) | 中端手机 (~50 万/秒) |
|---|---|---|---|
| 16 | 6.5 万 | 0.03 秒 | 0.13 秒 |
| 18 | 26 万 | 0.13 秒 | 0.5 秒 |
| 20 | 105 万 | 0.5 秒 | 2 秒 |
| 22 | 420 万 | 2 秒 | 8 秒 ⚠ 太慢 |

**默认 18；上限 22；前端算超过 3 秒则请求降难度重发。**

### 8.3 流程与校验

```
① POST /api/challenge        服务端生成 challenge，存 Redis：
                             cap:<challenge> = {action, difficulty, ip}，TTL 300 秒
② 前端 JS 暴力试 nonce
③ 提交时带上 {challenge, nonce}
④ 服务端校验：存在？未用过？动作匹配？哈希前缀为 0？
   ✓ 通过 ⇒ **先删再执行**（GETDEL，防重放）⇒ 执行操作
```

### 8.4 必须做对的四件事

```
① 题存服务端，不把答案编码进题里
② 一次性：验证前就删（原子 GETDEL）
③ 绑动作：登录的题不能拿去换搜索
④ 发题接口自己限速（否则有人刷你的 Redis/CPU）
```

### 8.5 局限（坦白）

```
✅ 挡得住：requests / curl 直接打接口的脚本
🔸 有限：会跑 JS 的爬虫（Playwright）—— 它们能算，只是变慢
❌ 挡不住：有 GPU 农场 / 代理池的定向攻击
⇒ PoW 的定位是"抬高低成本滥用的门槛"，不是防定向攻击
```

## 九、图片验证码（最终兜底 · 2026-11-04 所有者确认要做）

> 所有者原话：「验证码那个图片也做，作为最后的兜底，这个除了 OCR 扫描，
> 一般还是难以攻破的。」

### 9.1 它在整条链里的位置

```
第 0 层  429 + Retry-After           （当秒恢复，真人无感）
第 1 层  蜜罐字段 + 时间陷阱           （挡不动脑子的机器人）
第 2 层  PoW 工作量证明               （挡"会写脚本但不愿花钱"）
第 3 层  **图片验证码**  ← 本节       （挡"连算力都愿意花"的）
第 4 层  短封（5 分钟起，自动过期）     （人工/自动，最后手段）
```

**定位：不是为了"防住所有机器人"，而是让每一次自动请求都变得更贵。**
OCR 打码平台大约 1 美元/1000 次 —— 我们的目标是让"刷这个站的性价比"低于"正常用"。

### 9.2 触发条件（什么时候弹图）

```
① 登录：同一用户名失败 ≥ 5 次（第 6 次起必须过图）
② 登录：同一 IP 失败 ≥ 20 次 / 15 分钟
③ 匿名搜索：同一 IP 在 60 秒内被 429 达 10 次
④ PoW 通过后仍在 60 秒内超限（说明是"会算的脚本"）
```

**正常用户永远不会看到它**：上述条件对真人来说都不可达。

### 9.3 生成（服务端，Pillow）

```
字符集   4 位，去掉易混字符：不含 0O1lI、不含大小写同形
绘制     随机字体尺寸/位置 + 2~3 条干扰线 + 噪点 + 轻微旋转（-15°~+15°）
背景     浅色随机渐变（不要纯白，纯白更容易 OCR 预处理）
返回     image/png
        ⚠ 响应头必须带 Cache-Control: no-store（否则被中间层缓存 ⇒ 一张图反复用）
```

### 9.4 存取（关键：答案不能给客户端）

```
生成时：
  token = secrets.token_urlsafe(16)
  Redis: cap:img:<token> = {answer: "a7k2", action: "login", ip: <ip>}, TTL 300
  图片响应里**只带 token**（隐藏字段或响应体），⛔ 不要放进图片 URL（会进日志/Referer）

校验时：
  GETDEL cap:img:<token>              ← 原子取出并删除（一次性）
  与用户输入比较：忽略大小写、去空格
  action 必须匹配（登录的图不能拿去换搜索）
```

### 9.5 防滥用（图片本身也是资源）

```
· 发图接口自己限速：每 IP 每分钟最多 5 张（否则有人刷图打你的 CPU）
· 每个 token 最多校验 3 次，超出即作废（防"猜 1000 次"）
· 失败也计入审计（kind=rate_limited 或专门一类），便于以后看攻击形态
· 图片尺寸固定小（如 120×40），单张 CPU 成本约 1~3 ms
```

### 9.6 无障碍（不做会挡住真人）

```
· 「看不清？换一张」（重新发图，旧 token 作废）
· 提供**纯文字备选**：把同一道题显示成文字（"请输入图中的 4 个字母"），
  并允许屏幕阅读器读到（alt 文本或独立段落）
· 不给"语音验证码"（成本高、收益低，本阶段不做）
```

### 9.7 依赖与代价（要如实记账）

```
+ Pillow（约 3 MB，PIL fork，HPND 许可）
  ⇒ 会进 requirements.txt ⇒ 以后每天的 pip-audit 会一起扫它
  ⇒ 构建时间 +几秒，镜像体积 +几 MB
+ 一套模板/字体文件（可选，用系统自带 DejaVu 也行）
- 不做：不引入任何第三方验证服务（Turnstile / reCAPTCHA / 打码平台）
```

### 9.8 局限（坦白）

```
✅ 挡得住：只要"能发请求"的脚本（它们不会去接 OCR）
🔸 有限：接打码平台的（约 1 美元/1000 次，延迟 1~3 秒/次）
❌ 挡不住：愿意为"单次请求"付 1 分钱且有耐心的定向攻击
⇒ 所以它排在第 3 层，后面还有"短封"兜底
```

### 9.9 验收标准

```
· 未通过验证码时提交 ⇒ 400（不是 500，也不是"静默失败"）
· 同一 token 第二次使用 ⇒ 400
· token 过期（>5 分钟）⇒ 400
· 「换一张」后旧 token 失效
· 发图接口每分钟第 6 次 ⇒ 429
· 正常用户：一次输对 ⇒ 直接进入，不再弹图
```

## 十、登录失败计数（当前最大缺口）

```
不存在的：现在登录只写一条 login_fail 审计，没有任何拦截

设计：
  计数键  rl:login:user:<username>      失败 +1，成功清零，TTL 15 分钟
          rl:login:ip:<ip>              同上
  判定    用户名 ≥ 5  ⇒ 延迟 2 秒；≥ 6 ⇒ 锁 15 分钟（返回"稍后再试"）
          IP ≥ 20    ⇒ 该 IP 的登录要 PoW
  ⚠ 关键：**成功一次立刻清零**；延迟/锁定只作用于失败者
```

**为什么这样不会把你自己关在外面**：你输对密码 ⇒ 一次成功 ⇒ 计数清零。

## 十一、封禁策略（人工 + 短封）

```
① 默认带时长（5 分钟起），**自动过期**
② 后台显示倒计时与原因（避免"一堆僵尸规则"）
③ 住宅 IP 上限 24 小时
④ 登录用户优先按账号处置，不动 IP
⑤ 收回"永久封"选项（或只对机房段开放）
```

## 十二、实施前置条件（★ 现在绝对不能做）

```
1  隧道**覆盖**写 X-Forwarded-For（⛔ 不能追加客户端带来的值）
2  nginx 打开 realip：
     set_real_ip_from <隧道所在网段或 127.0.0.1>
     real_ip_recursive on
   ⛔ 现在打开 = 客户端自带的 XFF 会被当成真实 IP（比不开更糟）
3  proxy_set_header X-Forwarded-For 从"追加"改为 `$remote_addr`（覆盖）
4  80 端口从 0.0.0.0 改为 127.0.0.1（外网只能经隧道进）
5  ★ 完成 1~4 之后，client_ip 才可信 ⇒ M1/M3/nginx 限流才有意义
```

⚠ 顺带要重定 `is_bannable()` 的白名单：隧道如果在容器内，它的地址会是内网段。

## 十三、实施计划（分阶段，可回滚）

| 阶段 | 内容 | 依赖 | 预计 |
|---|---|---|---|
| **P0** | 写本文档、参数定稿 | — | 已完成 |
| **P1** | 登录失败计数（用户名 + IP） | 无（不依赖真实 IP）| 半天 |
| **P2** | 写操作限流（发布/删除/导出） | 无 | 半天 |
| **P3** | 删/降级设备令牌（按第六节结论）| P1/P2 之后 | 半天 |
| **P4** | 隧道就绪 → realip → nginx 限流（连接数/速率）| **等隧道** | 半天 + 联调 |
| **P5** | PoW（挑战生成/校验/难度自适应）| P4 之后 | 1~2 天 |
| **P6** | **图片验证码**（生成/校验/一次性/无障碍）| P5 之后 | 1 天 |
| **P7** | 封禁改造（短封 + 倒计时 + 不永久封住宅 IP）| P4 之后 | 半天 |

### 验收标准（每阶段）

```
P1  同一账号连错 5 次 ⇒ 第 6 次被拒；输对一次 ⇒ 计数清零；其他人不受影响
P2  连发 40 次发布请求 ⇒ 第 31 次 429；导出第 6 次 429
P3  匿名请求不再带 at_device cookie；搜索限流仍按 IP 生效
P4  伪造 XFF 不生效；nginx 日志里出现真实 IP；单 IP 并发 40 ⇒ 第 31 个连接 429
P5  不带 nonce 直接调接口 ⇒ 400；带正确 nonce ⇒ 200；同一个 nonce 二次使用 ⇒ 400
P6  验证码：未过图提交 ⇒ 400；同 token 二次用 ⇒ 400；过期 ⇒ 400；换图后旧 token 失效；
    发图第 6 次/分钟 ⇒ 429；正常人一次输对即通过
P7  封 5 分钟的 IP，5 分钟后自动解；后台显示剩余时间
```
