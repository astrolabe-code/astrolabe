## U0 一句话结论

> ★ **别做成「一条等级线」，要做成「三条正交的线」。**
> 用户提的五档里，**「VIP」和「管理员」不是同一种东西** ——
> 一个是**配额档**，一个是**职权档**。混成一条线，第一次改动就会打架。

## U1 ★★ 先拆维度（本文件最重要的一节）

用户提的五档：**游客 → 普通 → VIP → 企业 → 管理员**。
这条线**看起来**是一维的，其实混了**三件互不相干的事**：

| 线 | 取值 | ★ 决定什么 | ❌ **不**决定什么 |
|---|---|---|---|
| **① 登录态** | 游客 / 已登录 | ★ **能不能「写」**（解释 / 提问 / 笔记 / 阅读路径） | ❌ **不决定能不能读** |
| **② 站点职权** | `user` / `staff` / `superuser` | ★ **能不能「管站」**（审核 / 下架 / 参数 / 封禁） | ❌ 不决定配额 |
| **③ 订阅层级** | `free` / `vip` | ★ **「消耗服务器资源的能力」+「荣誉与成就感」**（见 U2.3 · U7） | ❌★ **绝不决定内容可读性** |

### ★★ 为什么必须拆开

★★ **如果做成「等级越高、看得越多」，会当场杀死本平台的核心机制**：

> `README` 与 `PRODUCT-VERSIONS.md` 都写明，公开版的价值是
> ★ **「1000 个人读同一个项目 = 1 张图 + 1000 份解释」**。
> 而这句话成立的前提是 —— ★ **每个人看到的是同一份内容**。

⇒ ⚠ 一旦"VIP 才看得到别人的解释"，**这个机制直接崩塌**：
每个人看到的都是**孤岛**，解释不再累积，产品退回到"又一个 AI 问答网站"。

★★ **结论（要写进纪律）**：

> **公开版的「读」对所有登录用户**永远平等**。**
> **VIP 卖的是「做得更多 / 更快」，❌ 不是「看得更多」。**

> ⚠★ **唯一的例外：付费项目**（见 **U9**）—— ★ 但**边界必须守死**：
> ★★ **锁「讲解」，❌ 不锁「结构」**（★ **代码与图永远免费**），
> 且 ★ **作者可随时改为免费** + ★★ **必须支持「到期自动转免费」**。
> ⚠ 详见 **U9.2**（能锁什么）与 **U9.5**（保护共享的保底机制）。

### ★ 三条线怎么组合（判定顺序）

```
① 能不能读？  ← 看【项目可见性】+【登录态】   （❌ 与 tier 无关）
② 能不能写？  ← 看【登录态】+【限流】         （❌ 与 tier 基本无关，tier 只给更高阈值）
③ 能不能管？  ← 看【站点职权】                （❌ 与 tier 完全无关）
④ 能建多少？  ← 看【订阅层级】+【配额表】
```

★ **判定顺序很关键**：先判「能不能读」，**再**看 tier。
❌ 反过来（先看 tier）就会写出"VIP 才能读某些内容"这种把结构带歪的代码。

### ★ 档位收敛（`B133` · 用户裁定）

> ★★ **公开版只有四个身份：游客 · 普通用户 · VIP 用户 · 管理员。**
> ⚠ **「企业用户」不是公开版的一个档位** —— 它是**另一个部署形态**
> （企业版 · 客户内网 · `PRODUCT-VERSIONS.md` B3）。
> ★ 因此公开版的 `tier` 只有 **`free` / `vip`** 两个取值，❌ 不含 `enterprise`。
> ⚠ 但**权限模型里仍给它留常量**（理由见 U2.4）。

## U2 各档职责与权限

> ★ 每档都分 **能做什么（正面清单）** / **明确不能做什么（反面清单）** / **判据（怎么判）**。
> ⚠ 反面清单**比正面清单重要** —— 它是防手滑的那一半。

### U2.1 游客（未登录）

| | |
|---|---|
| **是谁** | 从搜索引擎 / 分享链接进来的人，**没有账号** |
| ✅ **能** | ★★ **打开网站就能看到「用户选择公开的项目」**（首页 / 广场 —— ★ 这是**门面**）<br>★ **看图**：概览 / 节点列表 / 节点详情 / **多跳邻域** / 搜索<br>★ **读**解释、提问、阅读路径<br>★ 看创作者主页与徽章墙 |
| ❌ **不能** | 写任何东西（解释 / 提问 / 笔记 / 阅读路径 / 关注）<br>建项目 / 触发解析 / 发布<br>上传头像 |
| **判据** | `request.user.is_authenticated == False` |

> ★★ **设计意图（用户原话：「任何人打开网站，就能看到用户选择公开的项目」）**：
> **公开项目 = 网站的门面**，★ **游客必须能完整走完「打开项目 → 沿调用链读 → 看懂」**。
> ⚠ 否则**没人会注册**：如果第一屏就要登录，转化率会掉到接近零。
> ★ 只有在**他要留下点什么**的时候，才要求登录
> （"你想把这条笔记留在这里吗？登录后它就**永久钉在这段代码上**"）。
>
> ⚠ **由此推出一条实现约束**：★ **首页不登录也能用，且必须真的有用** ——
> ❌ 不能做成"游客只看到一张宣传图 + 登录按钮"。

### U2.2 登录普通用户（`tier = free`）

| | |
|---|---|
| **是谁** | 用 GitHub / Gitee 登录的**一般开发者** —— 既是**学习者**，也可能**发布自己的项目** |
| ✅ **能** | 游客全部 **+**<br>★ **写 UGC**：解释 / 提问 / 回答 / 笔记 / 阅读路径（`B109`：任何登录用户都可以写，**不要求你拥有这个项目**）<br>★ **发布自己的仓库**（★ **必须过 Gate 0 归属验证**，见 U3）<br>★ 关注 / 收藏 / 认领自己的项目 / 认领外部媒体署名<br>★ 编辑 / 删除**自己写的**条目 |
| ❌ **不能** | 管理站（审核 / 下架 / 改参数 / 封禁）<br>发布**不属于自己**的仓库<br>发布 **Fork**（★ 见 U3.2）<br>看**别人的**私有项目 |
| **判据** | 已登录 **且** 该动作通过对应检查（归属 / 限流 / 配额） |

★★ **两条最容易被搞错、必须写死的规则**：

| # | 规则 | 依据 |
|---|---|---|
| **1** | ★★ **写解释 / 提问 / 笔记，❌ 不需要你拥有这个项目，❌ 也不需要项目所有者同意** | `backend-design.md`「UGC 写权不依赖 can_edit」；★ 否则「1000 份解释」永远攒不起来 |
| **2** | ★ **编辑权只属于作者本人** —— ❌ **不提供「编辑他人的解释」**；替代方式是**并列新增**或**提议修订**（★ 保全署名与可追责） | 契约 §20.2「不得原地编辑他人内容」 |

> ⚠ 第 1 条是**反直觉**的：直觉会说"这是别人的项目，凭什么让你写？"
> ★ 但本平台的价值恰恰在于**允许陌生人在你的图上补充解释**。
> ⇒ 项目所有者能做的不是"禁止别人写"，而是**采纳（adopt）**某条答案作为**官方解释**。

### U2.3 VIP 用户（`tier = vip`）

| | |
|---|---|
| **是谁** | 愿意付费的**重度使用者**：要发布多个项目 / 仓库很大 / 想更快出图 / 想要更好看的徽章与更多曝光 |
| ✅ **能** | ★ **普通用户的全部**（★ 是**超集**，❌ 不是"另一个人群"）**+** 两类东西：<br>★★ **① 消耗服务器资源的能力**（用户原话）—— **更多解析节点 · 更强的解析与图能力**：<br>　· 更高配额（项目数 · 仓库大小 · **文件数** · 解析并发，见 U6）<br>　· **优先队列**（同样排队，★ **VIP 先出图**）<br>　· **深度分析（加速器池）**：>2 跳 / 全图算法（⚠ 仍需管理员开通，契约 §17.7）<br>★★ **② 荣誉与成就感**（用户原话：「**花哨、但比较让人有成就感的功能**」）：<br>　· ★ **徽章的展示方式**（更多展示位 · 自定义陈列 · 花哨样式与动效，见 U7.4）<br>　· **成就进首页 / 发现页**（更多曝光）<br>　· 创作者主页的**强化样式** |
| ❌ **不能** | ★★ **看更多内容**（❌ 不能看别人的私有项目、❌ 不能看"VIP 专属解释"）<br>★★ **买"学习成就"勋章**（★ 只能买"**展示方式**"，见 U7.4）<br>★ **不受限流**（仍限流，只是**阈值更高**）<br>★ **勋章获得条件放宽**（★ 条件对所有人一样，❌ 不能"充钱免做"）<br>管理站 |
| **判据** | `UserProfile.tier == "vip"` **且** 该能力在能力表里（U5） |

★★ **两句话把 VIP 定死**：

> **① VIP 是「配额 + 荣誉档」，❌ 不是「权限档」。**
> **② VIP 卖的是「花更多的服务器资源」+「更好看的勋章」，❌ 不是「看到更多别人的知识」。**

⚠ 这两条要成为**产品纪律**写进任何对外文案 ——
❌ 绝不能出现「升级 VIP 解锁全部解释」这种话术：**那是在卖别人的知识**；
❌ 也不能出现「VIP 免做任务直接拿勋章」：**那会让所有勋章立刻贬值**（U7.4）。

### U2.4 企业用户 —— ★ **不是公开版的一个档位**

★★ **用户已裁定（`B133`）**：企业用户**划归企业版**（`PRODUCT-VERSIONS.md` B3）——
★ **公开版的四个身份里没有它**（见 U1「档位收敛」）。

| | |
|---|---|
| **它是什么** | ★ **另一个部署形态**：客户**内网**部署，用户由客户的 **SSO / 目录**产生，❌ 不经过公开版注册 |
| **公开版里怎么处理** | ★ **不提供这一档**；`tier` 只有 `free` / `vip` |
| **为什么还留常量** | ★ `PRODUCT-VERSIONS.md` **F 节**原话：「★ **这些功能一期就要「可开可关」地设计，别写死**」<br>⚠ 一个开关都不留 ⇒ 将来把企业功能"收回公开版付费层"时要**重写权限层** |
| **留位的代价** | ★ **几乎为零** —— 只在能力表里多一行、`tier` 枚举里多一个常量 |

> ★★ **关键提醒**：★ **企业版与公开版不应共用同一套权限判定** ——
> 它的身份来自**客户自己的目录**，而公开版的身份来自 **GitHub / Gitee OAuth**。
> ⚠ 强行共用会让"公开版权限层"长出企业专用分支（★ 这正是 `ARCHITECTURE.md` 最怕的「长成一坨」）。

### U2.5 管理员（★ 建议拆成两档）

★ 用户说的是"掌管整个网站行为和参数的**管理员**"。我建议**拆成两档**，理由是**这两件事的风险差一个量级**：

| 档 | 取值 | 管什么 | 典型动作 |
|---|---|---|---|
| **运营（staff）** | `is_staff = True` | ★ **处理内容** | 审核 A/B/C 车道 · 下架 · 处理举报 · 封禁违规用户 · 看审计 |
| **超管（superuser）** | `is_superuser = True` | ★ **改规则本身** | 改 **`AppSetting` 参数** · 开关功能 · 授予/撤销 staff · 重建索引/缓存 · **特批**（唯一例外：允许 zip 项目公开） |

★★ **为什么要拆**：**运营是日常、高频、可轮班；改参数是低频、不可逆、要一个人负责。**
⚠ 合成一个"管理员"后，**招一个实习生做审核就等于给了他改全站参数的权力**。

#### 管理员的三条纪律（★ 最容易出的问题都在这三条上）

| # | 纪律 | 为什么 |
|---|---|---|
| **1** | ★★ **每一个管理动作都必须留审计**（含**读**了用户内容） | 「掌管整个网站」= 权力最大 ⇒ ★ **可追责**是它唯一的约束；⚠ 读私有内容**也要记一笔** |
| **2** | ★★ **管理员不能随便改图** —— 图由**服务端解析作业**唯一产出（`B103`） | 唯一例外是 `GRAPH-STORAGE.md` G1 的**维护者手工修补**：<br>★ 必须 `origin = manual` + **全量审计** + **`GraphRevision.rev + 1`**（否则邻域缓存不失效） |
| **3** | ★ **管理员看不到密码 / token 明文** | ★ 本来就不该存 —— 只存哈希（契约 §12：`blake2b(raw, digest_size=32)`）；⚠ 这条是**架构保证**，不是靠自觉 |

> ★ **「特批」是唯一一处允许把「不该公开的东西」放行的口子** ——
> 依 `B109`：「zip 项目不能公开，**除非管理员同意**」。
> ⚠ 因此**特批必须单独记一条审计**，且**申诉/下架流程要能追到是谁批的**。

## U3 ★★ 「用户只能拉他自己的 GitHub 库」怎么实现

> ★ 这是本次讨论里**最硬的一条技术要求**，也是整个发布链路的**第一道门**。
> ★ 对应 `backend-design.md` 的 **Gate 0（第三方身份与归属验证）**。**核心一句话：**

### U3.1 完整链路（四步，缺一不可）

```
① 身份绑定   GitHub/Gitee OAuth 授权
             ⇒ 拿到 ★ provider_user_id（数字 ID，不可变）+ login（用户名，会改）
② 归属校验   GET /repos/{owner}/{repo}
             ⇒ ★ repo.owner.id == 绑定的 provider_user_id
③ Fork 拒绝  repo.fork == true
             ⇒ ★ 拒绝（提示「这是 Fork，请去原作者仓库发布」）
④ 许可核验   仓库根有许可证 且 允许再分发（B109：许可分级 + L1 核验）
             ⇒ 通过后才允许投递解析作业
```

★ **四步全过 = 允许服务端拉取**。❌ 任何一步不过 ⇒ **拒绝并给出可读原因**。

### U3.2 ★★ 三个真实的坑（现在不定，实现时必踩）

| # | 坑 | 后果 | ★ 建议口径 |
|---|---|---|---|
| **1** | ★★ **GitHub 用户名可以被改** | ⚠ 只比 `login` 字符串 ⇒ **用户改个名，归属校验就失效**（或把自己的验证过了） | ★★ **必须存 `provider_user_id`（数字 ID）并比它**；`login` 只用于展示 |
| **2** | ★★ **组织（Organization）名下的仓库** | ⚠ 组织仓库的 `owner.login` **不是** 你的用户名 ⇒ **一律被拒** | ★ **一期明确只放行「个人仓库」**；⚠ 组织仓库**列入待办**（需 GitHub App 安装 + 组织授权），★ 且它与 `PRODUCT-VERSIONS` B3 **企业版**范畴一致 ⇒ 公开版不做 ✅ 自洽 |
| **3** | ★ **Fork** | ⚠ 你是 fork 的所有者，但**代码不是你写的** ⇒ 放行等于**替别人转发** | ★ **一律拒绝**；`repo.fork / repo.parent` 判据；⚠ `backend-design.md` 明确「**不因"你是 fork owner"而放行**」 |

### U3.3 ★ 权限申请范围（最小权限，必须守）

| | |
|---|---|
| ★ **建议** | 优选 **GitHub App（细粒度权限）**；退一步用 **OAuth App + `read:user`** |
| ★★ **明确不申请** | ⚠★ **任何读私有仓库的权限** —— 本平台**不需要**看用户私有代码（`PRODUCT-VERSIONS` B1：**禁止私有源码上行**） |
| ★ 为什么够 | 校验**公开仓库**的归属，用**公开信息**就够了 —— `read:user` + 公开 API 即可 |
| ⚠ 用户感知 | ★ 授权页上**权限越少，越多人敢点** —— 这是**转化率**问题，不只是安全问题 |

> ★ **收尾**：`repo.owner.id == provider_user_id` 成立 **≠ 拥有版权**。
> ★ 官方文案**只能写「已验证账号归属」**，⚠ **绝不能写「已验证版权」**（契约 §20.7）。

### U3.4 ★★ 许可核验（★ 第三道门）

> **用户原话（`B142`）**：「拉的时候，要检查……**许可证能支持在我这个站上解析**。」

⚠★ **这里有一个必须分清的法律判断**：

> ★★ **「在本地解析」与「把解析结果公开到网站」，是两种不同的行为。**

| 行为 | 需要什么 | 说明 |
|---|---|---|
| ★ **在本地解析**（读源码、生成图） | ★ **基本都允许** | ★ 属于**技术处理**，一般不构成侵权 |
| ★★ **把「图」公开到网站** | ★★ **需要许可证允许「再分发」+「制作衍生作品」** | ★★ 因为 ★ **图是源码的衍生结果** |

⇒ ★★ **所以判据不是"能不能解析"，而是「许可证允不允许把衍生结果公开」。**

#### ★ 许可分级（★ 落实 `B109` 的"许可分级"）

| 许可证 | 自动放行？ | 说明 |
|---|---|---|
| **MIT · Apache-2.0 · BSD · ISC · Unlicense** | ✅★ **自动放行** | ★ 宽松许可，**允许再分发与衍生** |
| **GPL-2.0 · GPL-3.0 · AGPL · LGPL** | ⚠★ **人工复核** | ★★ 见下（★ **传染性**问题） |
| **限制性许可**（Elastic / PolyForm / BSL） | ⚠★ **人工复核**（★ 标注「**明确限制条款**」） | ★ 作者**是版权人 ⇒ 可以授权给自己** ⇒ ★ **可放行**，但 ⚠ 平台是**"明知条款存在"** |
| **无许可证文件** | ⚠★ **人工复核**（★ `B143` 用户裁定） | ★ 默认**保留所有权利**；★ **但提交者本人很可能就是权利人** |

★★ **修正（`B143`）**：★ **"无许可证"与"限制性许可"从「立即拒绝」改为「人工复核」**。
★ 理由见 **U3.7**（★ 很实在：**用户自己的 GitHub 项目大多没有许可证**，
⚠ **若直接驳回，他连自己的库都测不了**）。

#### ★★★ 为什么 GPL 要「人工复核」而不是「直接放行」

★★ 这是一个**真实的坑**，值得单说：

> ★ **GPL 代码的「调用图」算不算「衍生作品」？**
> ★ 如果算 ⇒ ★★ **我们的图数据可能要按 GPL 发布**（★ 传染性）⇒ ⚠ **影响整个平台的数据许可**。

★ 这是**有争议的法律问题**（业界无统一结论）⇒ ★ **不建议自动放行**；
★★ 但 **GPL 项目（含 Linux 内核）数量巨大** ⇒ ★ ❌ **也不要一律拒绝**。

★ **建议**：★ **列入人工复核**，★ 由管理员逐个判断（★ 这正是 `B109`「许可分级」的用途）。

> ⚠ **一期只接受「仓库根有许可证文件」的项目**（★ 便于自动判定）；
> ★ 没有许可证文件的 ⇒ ❌ **默认拒绝**，★ 但允许作者**补上许可证后重新提交**。

### U3.5 ★★ 举报与处理流程（★ 用户：「依旧要有举报途径」）

> **用户原话（`B142`）**：「最后，**依旧要有举报途径**，告诉我**某个作者侵权了**，
> 我可以**检查，然后下架或隐藏他的项目**。」

★ 但建议**把「隐藏」与「下架」分开** —— ★ 它们是两个力度不同的动作，⚠ 混用会出问题：

| 动作 | 效果 | ★ 什么时候用 |
|---|---|---|
| ★ **隐藏（unlist）** | ★ 从**列表 / 搜索 / 首页**消失，★ **直接链接仍可访问** | ★★ **存疑但未定论** —— 收到举报、**还在核查** |
| ★★ **下架（takedown）** | ★ **彻底不可访问**（→ 404） | ★★ **确认侵权** |

★★★ **为什么要分两级**（★ 三方都有利）：

| 谁 | 为什么有利 |
|---|---|
| ★ **举报人** | ★ **立刻就能止损**（★ 隐藏已经让它不再扩散） |
| ★★ **被举报人** | ★★ **没被一刀切** —— ★ 还在核查，❌ **不是定罪** |
| ★ **平台** | ★ **"收到通知后及时采取措施"有据可查** ⇒ ★ 这是**避风港的要件** |

#### ★★ 完整流程（★ 关键是第 ④ 步，⚠ 别漏）

```
① 举报        任何人都可以举报，★ 必须指定理由
      ↓
② 隐藏        ★ 默认先「隐藏」（★ 不是直接下架）
      ↓
③ 通知被举报人  ★ 给出具体理由 + 证据
      ↓
④ ★★ 被举报人可以申辩（★ 反通知）
      ↓
⑤ 管理员裁决   ★ 恢复 / 维持隐藏 / 下架
      ↓
⑥ 留审计      谁举报 · 谁裁决 · 依据哪一条（AuditLog）
```

★★★ **第 ④ 步最容易漏，但它很重要**：

| # | 为什么必须有申辩 |
|---|---|
| **1** ★★ | **防误伤** —— ★ 与 `U9.9`「**误杀比放过更伤人**」同一原则 |
| **2** ★★ | **法律上更完整** —— ★ **"给被举报人申辩机会"是正当程序的体现** |
| **3** ★ | ★ 他自己的文档里**已经写了**：★ 契约 §20.2「删除为**软删除 + 可申诉**」 |

★ **举报理由清单**（★ 与 `U9.9 ③` **共用一套**）：
★ 侵权 · 归属不实 · 无许可证 · 二次收费 · 内容没实质 · 其他。

### U3.6 ★★★ 诚实边界：「已尽到合理注意」**≠**「零风险」

> **用户原话（`B142`）**：「这样，**在法律上我已经做到极致了**，
> 甚至**比 github 和 B站这些防侵权做的还多**。」

★ **"比别人做得多" ✅ 这一点成立**：

| | GitHub | B 站 | ★ **本平台** |
|---|---|---|---|
| **验证"你是作者"** | ❌ 谁都能 fork / clone | ⚠ 不验证（UP 主可能是转载者） | ✅★ **归属验证** |
| **排除 fork** | ❌ | ❌ | ✅★ **排除** |
| **许可核验** | ⚠ 只提示 | ❌ | ✅★ **作为放行门槛** |

★★ **但"做到极致" ❌ 不等于"零风险"** —— ★ 有几件事**技术上做不到**：

| # | 做不到的 | 为什么 |
|---|---|---|
| **1** ★★ | ★★ **归属 ≠ 版权** | ★ 这是他文档里的原话（`backend-design.md` E25）：<br>⚠ "repo.owner == 授权账号" 只能证明 ★ **这个账号拥有这个仓库**，<br>❌ **不能证明他拥有代码的版权** —— ★ 例如：★ 他把**别人的代码**传到自己仓库 |
| **2** ★★ | ★ **fork 标记可以绕过** | ★ 下载别人的代码、**新建一个仓库**上传 ⇒ ★ **`fork == false`，但代码是抄的** |
| **3** ★ | ★ **许可证文件可能谎报** | ⚠ 写着 MIT，实际内容是别人的私有代码 |
| **4** ★ | ★ **改写 / 洗稿** | ⚠ 换语言、改改变量名 ⇒ ★ **技术上无法自动判定** |

#### ★★★ 所以正确的定位是（★ 这句话要变成对外文案纪律）

> ★★ **不是"零风险"，而是「已尽到合理注意义务 + 有完整的通知-删除通道」。**
> ★ 这正是**避风港（safe harbor）**的核心 ——
> ★★ **平台不是「保证没有侵权」，而是「不知道 · 没参与 · 收到通知就处理」。**

#### ⚠★ 一条对外文案纪律（★ 很反直觉，但很重要）

| | 文案 |
|---|---|
| ❌ **不能说** | ★「我们已**杜绝**侵权」「我们**保证**所有内容合法」「**已验证版权**」 |
| ✅ **可以说** | ★「我们做了**归属验证 / fork 排除 / 许可核验**，并设有**举报与处理通道**」 |

★★★ **为什么不能说"杜绝"**：

> ⚠ 一旦真的出现侵权，★ **"你说了你杜绝了"会被用来证明你「明知」** ——
> ★★ 而这**恰恰是避风港最怕的**（★ 避风港的前提是"**不知道**"）。

★ 特别提醒（★ 与契约 §20.7 一致）：

> ★ **只能说「已验证账号归属」，❌ 不能说「已验证版权」。**

### U3.7 ★★★ 审核队列必须显示「为什么进审核」（★ `B143` 用户裁定）

> **用户原话**：
> 「**没有许可证的不要立即驳回，依然是管理员审核** ——
> 这是方便我**前期测试**的手段，我**很多 github 项目也没有许可证**，我就不能测试我自己的库了。
> ★★ 当然，**以后我是不会放行没许可证的**，
> ★★★ 所以，**审核里一定要显示表明为什么进审核**。」

#### ★★ 为什么不能"立即驳回"

★★ 用户给了一个**很实在的场景**：★ **他自己的项目大多没有许可证** ⇒
⚠ **若"无许可证"直接拒绝，他连自己的库都测不了。**

★★ 而更根本的是：★ **"无许可证" ≠ "侵权"** ——

| | 事实 |
|---|---|
| ★ **法律状态** | ★ 默认**保留所有权利**（★ 没有授权） |
| ★★ **但权利人是谁** | ★★ **很可能就是提交者本人** —— ★ 他**不需要自己的授权** |

⇒ ★★ 所以"无许可证"是**风险信号**，❌ **不是"必然拒绝"** —— ★ **应当由人判断。**

#### ★★★ 审核队列的设计（★ 这一条比"改个分级"更重要）

★★ 用户说「**审核里一定要显示表明为什么进审核**」——
★ 这要求**每一条待审核项都必须自带「进审核的理由 + 判断依据」**：

| 显示什么 | 例 |
|---|---|
| **① 进审核的原因**（★ **人类可读**） | ★「**未找到许可证文件**」/「**GPL-3.0**（传染性，需人工判断）」/「**Elastic 2.0**（限制性条款）」 |
| **② 系统检测到的证据** | ★ 检测到的 **SPDX 标识** · **文件路径** · **原文片段（截断）** |
| **③ 系统的建议** | ★「建议放行」/「建议拒绝」+ **一句话理由** |
| **④ 提交者与仓库** | ★ 谁提交的 · 仓库地址 · commit · **绑定账号**（★ `U3.1` 归属校验结果） |

★ **决定权始终在管理员** —— ★ 系统只给**依据 + 建议**，❌ **不代替判断**。

#### ★★ 为什么"显示依据"是**法律上**必需的（★ 不只是好用）

> ★★ **"人工审核通过" ≠ "平台背书版权"。**
> ★ 它只表示 ★ **「在已知信息下，未发现明显问题」**。

⇒ ★★ 所以**审核记录里必须写清"我们看了什么、依据什么决定的"** ——
★★ 这样将来一旦出问题，平台能证明 ★ **"我们做了判断，而不是没看就放行"**。

★ 配合 `U3.6` 的文案纪律：★ 审核通过的正确说法是
★「**已通过许可核验**」，❌ **不是**「已验证版权」。

#### ★ 三条配套建议

| # | 建议 | 为什么 |
|---|---|---|
| **1** ★★ | ★ **"无许可证放行"要有显式标记**（如 `license_exception = true`） | ★ 便于**将来批量收回** —— ★ 用户说"**以后我是不会放行没许可证的**" ⇒ ★ 那时要能**一键筛出来** |
| **2** ★★ | ★★ **用一个开关 `license_require_file`** 控制"无许可证是否自动拒绝" | ★ **现在关**（便于前期测试）· ★ **以后开**（一开就收紧，❌ 不用改代码）—— ★ 这正是"**可开可关**"的用法 |
| **3** ★ | ★ **补上许可证后自动重判** —— 作者补了 `LICENSE` ⇒ 重新走分级 | ★ 让作者有一条**自己摘掉例外标记**的路 |

### U3.8 ★★★ 被驳回时，**用户必须能看到「为什么」**（★ 实现：`core/submission.py`）

> **用户原话**：「**申请要能驳回**，**用户要能看见自己的申请被驳回的原因**。」

#### ★★ 两条推导出来的硬要求

| # | 要求 | 为什么 |
|---|---|---|
| **1** ★★ | ★★ **驳回时必须填理由，❌ 不允许空理由驳回** | ⚠★ 没有理由的驳回，用户只看到"被拒绝了"却**不知道该改什么** ⇒ ★ **等于把审核变成黑箱**（★ 与 `U3.7`「显示依据」是同一个精神，只是**面向的人不同**） |
| **2** ★★ | ★ 用户能看到**自己的**提交记录与结论 | ★ 否则他会**反复重试**（★ **反而加重刷审核**） |

★ 实现上：★ `ProjectReview.reject()` **理由为空直接 `raise`** ——
★ 让它**在开发期就暴露**，❌ 不靠"审核员记得填"。

#### ★★ 给用户看的 ≠ 给管理员看的（★ 有意区分，不是一个字段两用）

| 字段 | 管理员 | 用户 | 说明 |
|---|---|---|---|
| `reason_text` | ✅ | ❌ | ★ 含**内部判断要点**（如"权利人可能就是你"） |
| `evidence` | ✅ | ❌ | ★ 检测证据细节 |
| `suggestion` | ✅ | ❌ | ★ 写的是"**建议人工确认提交者身份**"这类**工作台语言** |
| **`user_message`** | ⚠ 备查 | ✅ | ★★ **给提交者的说法**：说清**状态 + 该做什么** |
| **`decision_note`** | ✅ | ✅ | ★★ **驳回理由 —— 用户最需要的就是这一条** |

⇒ ★★ 一句话：**用户要看的是「我该做什么」，不是「我们内部怎么讨论你」。**

★ 实现落点：★ `submission.my_submissions()` 是**有意过滤过的投影**（❌ 不是 `values()` 全给）。

### U3.9 ★★★ 上传限额（★ 防刷审核 · 管理员可控 · 可给个别人放宽）

> **用户原话**：「还有一些**恶意刷审核**的，规定**一天或一周只能传几个项目**，
> **我不觉得一个人一天能做十几个解释**，那就类似 B 站的**水视频**了。
> 还有，这个**上传频率，管理员可控**，要是真有人，这么厉害，也得**给其创造空间**。」

#### ★★ 为什么"按提交计次"而不是"按通过计次"（★ 这条决定限额有没有用）

| 方案 | 结果 |
|---|---|
| ❌ **通过才计次** | ★★ 恶意刷的人**被驳回了也不占额度** ⇒ **可以无限刷** ⇒ **限额形同虚设** |
| ✅ **提交即计次** | ★★ 刷一次就少一次 ⇒ **防刷才真正成立** |

⚠★ 代价：★ **被误驳回的用户会亏额度** ⇒ ★ 所以**必须**配一个**退还**动作
（`reject(refund_quota=True)`）—— ⚠ 否则「退还」只是**安慰性字段**。

#### ★★ 计数必须来自「流水」，❌ 不能数 `Project` 表

⚠★ 因为：★ **用户把项目删掉、再传一次，就绕过了限额。**

⇒ ★★ 计数一律走 `ProjectReview`（**append-only 流水**），
且它的 `project` 外键必须是 **`SET_NULL`（❌ 不是 `CASCADE`）** + 冗余 `project_ref` / `project_name`
⇒ ★★ **项目删了，流水还在** —— 限额**绕不过去**。

#### ★★ 三级覆盖（复用 `U6` 的机制，❌ 不新造）

```
档位默认（代码常量） → 参数覆盖（管理员改 AppSetting） → 用户级覆盖（UserProfile.quota_override）
                                                             ↑
                                              ★★ 「给厉害的人创造空间」就改这里
```

★ 所以「给某个人放宽」**不需要改代码、不需要新表**：
★ 管理员往 `quota_override` 写一行即可（★ `{"project_per_day": 50, "project_per_week": 300}`）。
★★ **`project_per_day = 0` 表示「不限制」** —— 给官方账号 / 内部测试的彻底放行口子。

#### ★★ 四个防刷机制（缺一不可）

| # | 机制 | 挡的是什么 |
|---|---|---|
| **1** | ★ 日 / 周双窗口限额 | ★ 短时间灌一堆 |
| **2** | ★★ **同一仓库重复提交** | ★★ **单纯限次数挡不住「改个名字反复刷」** —— ⚠ 一天 3 次也能刷 |
| **3** | ★★ **`select_for_update` 锁用户行** | ★★ **并发绕过**：两个请求同时读到"还剩 1 个" ⇒ 双双通过 |
| **4** | ★ **管理员可整体关掉**（`quota.upload_limit`） | ★ 被刷爆时**先放开**，❌ 不用改代码 |

#### ★ 三个配套细节

| # | 细节 | 为什么 |
|---|---|---|
| **1** ★ | ★ **提示里必须带「下次什么时候能来」** | ⚠ 只说"你不能传了" ⇒ 用户**反复重试** ⇒ **反而加重刷审核** |
| **2** ★★ | ★★ **自动拒绝（材料不全）不扣额度** | ★ 那是"**补齐再来**"，⚠ 不该罚用户（★ 否则他改一次文件名就亏一个额度） |
| **3** ★ | ★ 日 / 周窗口用**本地时区** | ⚠ 用 UTC ⇒ 对东八区用户「一天」的边界在**早上 8 点** ⇒ ★ 他会觉得"说好一天 3 个，怎么刚过中午就没了" |

★★★ **实现**：`core/quota.py`（判定）+ `core/submission.py`（闸门）。

## U4 认证方式与注册开关（★ 已裁定：OAuth 为主 + **邀请制**）

### U4.1 建议

| 项 | 建议 |
|---|---|
| ★ **主要登录方式** | ★ **GitHub OAuth**（首选）/ **Gitee OAuth**（国内可用性 + 第二身份线） |
| ❌ **不提供** | ★ **用户名 + 密码注册 / 登录**（★ 理由见下） |
| ★ **管理员登录** | 走 **Django `/admin/`** 自带的密码体系（★ **与 API 认证物理分开**） |
| ★ 会话形态 | 浏览器端：服务端签发**自己的 API token**（Bearer），❌ 不用 Django session 走 API |

### U4.2 ★ 为什么建议不做密码登录（四条，都很实在）

| # | 理由 |
|---|---|
| **1** | ★ **目标用户 100% 有 GitHub** —— 他们是程序员；密码体系**几乎不增加覆盖** |
| **2** | ★★ **省掉一整套高危子系统**：弱密码拦截 · 撞库防护 · 密码重置邮件 · 邮箱验证 · 验证码 · 锁定策略 —— **这些是账号安全事件的主要来源** |
| **3** | ★ **省掉「防账号枚举」难题** —— 契约 §15.4 要求 `account_locked` / `weak_password` **不在登录响应中返回**；★ **没有密码就没有这个问题** |
| **4** | ★ **少一套凭据要保护** —— 没有密码库，就没有"用户密码泄露"这一整类事故 |

### U4.3 ⚠ 代价（诚实说）

| 代价 | 缓解 |
|---|---|
| ⚠ **依赖第三方可用性** —— GitHub 挂了就登不进 | ★ 保留 **Gitee** 作第二 provider；⚠ 且**已登录用户的 token 未过期时不受影响** |
| ⚠ 国内访问 GitHub 不稳 | ★ 同上（Gitee 就是为这个准备的） |
| ⚠ 用户可能想"不要绑定" | ★ **读不需要登录** —— 不绑定也能看；★ 只有**要写**的时候才需要 |

### U4.4 ★ 三条必须守的认证纪律（沿用既有口径）

| # | 纪律 | 出处 |
|---|---|---|
| **1** | ★★ **token 明文只返回一次**，库里**只存哈希**（`blake2b(raw, digest_size=32)`） | 契约 §12 |
| **2** | ★ **Bearer 免 CSRF；无 Authorization 头 ⇒ 走 session + CSRF**（三态判定） | 契约 §7 |
| **3** | ★★ **认证链路 fail-closed，读路径 fail-open** —— ⚠ 限流后端挂了**不放行登录**（否则"DoS 掉限流"就成了**暴力破解的绕过手段**） | 契约 §15.3 |

### U4.5 ★★ 澄清：「本站账号」与「登录方式」是**两件事**

> **用户原话（`B141`）**：「本站要有**登陆功能**，也就是在本站要**有账号**，**就像 B 站一样**。」

⚠ 这句话有一个**很容易混**的地方，先说清：

| | 是什么 | 结论 |
|---|---|---|
| ★★ **「本站有账号」** | ★ 用户在本站有**身份**：主页 · 徽章墙 · 作品集 · 关注关系 · 学习进度 | ✅★ **必须有**（`U7` / `U8` 全靠它） |
| ⚠ **「用本站的用户名 + 密码登录」** | ★ 只是一种**凭证方式** | ⚠ **建议不做**（`U4.2` 四条理由） |

★★ **两者不冲突**：

> ★ **「有账号」说的是【身份】，「怎么登录」说的是【凭证】。**
> ★ 本站**一定有账号**；★ 只是**登录时不输密码，而是走 GitHub / Gitee 授权**。

★ **B 站其实也是这个模式**：★ 你的 B 站账号绑定了手机 / 第三方，
★ 而你在 B 站的**身份**（等级 / 勋章 / 投稿）**不依赖于"有没有设过密码"**。

★ **所以结论不变**：★ **账号体系必须完整，登录方式只有 OAuth** ✅
⚠ 若你**坚持要密码登录**也可以 —— ★ 但要多做**整套安全子系统**（`U4.2` 已列），
★ 建议**等有真实需求再加**（★ 那时是**加法**，不是重写）。

### U4.6 ★★ 三个开关（★ 别混成一个）

> **用户原话（`B141`）**：「**这个登陆注册功能，可以由管理员控制**，
> 即**允许登陆**还有**允许注册**。」

★ 你要的是两个开关 ✅ —— ★ 但我建议**区分三个**，⚠ 因为它们的作用面**完全不同**：

| 开关 | 管什么 | ★ 影响谁 | 典型用途 |
|---|---|---|---|
| ★★ **`registration_open`** | ★ **新用户能不能注册** | ★ 只有**没账号的人** | ★★ **邀请制测试期**（★ 关掉它，靠邀请码放行） |
| ★★ **`login_open`** | ★ **能不能签新 token** | ★ 只有**未登录的人** | ★ 维护 / 限流 / 紧急刹车 |
| ★★★ **`paused`（关站门禁）** | ★ **整站是否停服** | ★★ **所有人（含已登录）** | ★ 法律风险 / 被攻击 / 严重故障 |

⚠★ **为什么必须把 `login_open` 与 `paused` 分开**：

> ⚠ 如果"关掉允许登录"会**把已登录的人也踢出去**，那它就是个**一键关站** ——
> ★ 那**不该叫"允许登录"**，★ 那是 `paused`。

★ 建议语义：★ **`login_open = false` 只拦"新登录"，❌ 不影响已有 token** ——
★★ 这样它是**温和的**（老用户照常用，新用户进不来），★ 而 `paused` 才是**重锤**。

★ 三者都放 `AppSetting`（★ 参数中心），★★ **改动必须留审计**（`U2.5` 纪律 1）。

### U4.7 ★★★ 邀请注册机制

> **用户原话（`B141`）**：
> 「**必须还有邀请注册机制**，我要先做一些**公开上线测试**，
> ★★ **不能让任何人都能注册，必须是我邀请到的人**。」

#### ★★ 为什么这个策略是对的

★★ 它其实是**「读开放 + 写邀请」**的组合 —— ★ 而这正是**冷启动的正确姿势**：

| | 策略 | 为什么 |
|---|---|---|
| ★ **读** | ★★ **完全开放**（连游客都能完整读，`U2.1`） | ★ **能被搜索引擎收录、能被分享** ⇒ ★ **有流量** |
| ★★ **写** | ★★ **邀请制** | ★★ **早期内容质量比数量重要得多** —— ⚠ 一个垃圾解释会**劝退**新读者 |

★★★ 一句话：★ **「让人随便看，但只让信得过的人写。」**

#### ★ 邀请的四种形态（★ 建议分期上）

| 形态 | 说明 | 一期 | 将来 |
|---|---|---|---|
| **A. 管理员生成邀请码** | ★ 明文码，一次性 | ✅★ **上** | ✅ 保留 |
| **B. 管理员生成邀请链接** | ★ 带**过期时间** + **邀请人** | ✅★ **上这个**（★ 比 A 好，见下） | ✅ 保留 |
| **C. 用户邀请额度** | ★ 每个用户有 N 个邀请名额 | ❌ | ★ 增长期再上（★ B 站早期就是这样） |
| **D. 管理员手工建号** | ★ 最土但最可控 | ✅（`/admin/` 已有） | ✅ 保留 |

★★ **为什么推荐 `B`（链接）而不只是 `A`（明文码）**：

| | 明文码 | ★ 邀请链接 |
|---|---|---|
| **能不能带过期** | ⚠ 要额外记 | ✅ **天然可以** |
| **能不能带邀请人** | ⚠ 要额外记 | ✅ **天然可以** |
| **能不能被猜** | ⚠★ **短码可以被爆破** | ✅★ **长随机串，猜不到** |

#### ★★ 四条必须写死的规则

| # | 规则 | 为什么 |
|---|---|---|
| **1** ★★ | ★ **邀请「用一次即失效」**（或限定次数） | ⚠ 否则一个码泄露 = **无限注册** |
| **2** ★★ | ★ **必须有过期时间** | ⚠ 否则**泄露了就永久有效** |
| **3** ★★★ | ★ **必须记录「谁邀请了谁」** | ★★ **邀请制 = 连带责任** —— ★ 有人邀请垃圾账号进来，**要能找到邀请人**（★ 与"署名 / 可追责"同一理念） |
| **4** ★★ | ★ **通过邀请进来的用户 = 普通用户（`free`）** | ⚠ **❌ 不能通过邀请拿到 VIP** —— ★ VIP 只与付费 / 授予有关（`U6`） |

#### ★ 数据形状（见 `U10`）

| 模型 | 关键字段 |
|---|---|
| `Invite` | `token`（★ 长随机 / 签名） · `created_by` · `expires_at` · `max_uses` · `used_count` · `note` |
| `UserProfile.invited_by` | ★ **FK → 邀请人**（★ 放 `UserProfile`，❌ 不往 Django `User` 上加字段 —— `U10` 纪律 2） |
| `AppSetting` | `registration_open` / `login_open` / `paused`（★ 见 `U4.6`） |

### U4.8 ★★★ OAuth 首次登录 = **注册**（★ 最容易漏的一个洞）

★★★ **这是本节最容易做错的地方，必须写死**：

> ⚠★ **如果只给"注册页"加邀请码，而"从 GitHub 登录"这条路径不加** ——
> ★★ **任何人都能靠"用 GitHub 登录一次"绕过邀请制。**

#### ★ 正确流程

```
① 访问登录页
        ↓
② 若【没有账号】⇒ ★ 必须先填【邀请码 / 走邀请链接】
        ↓   （★ 校验：有效 · 未过期 · 未用尽）
③ 存进 session，跳转 GitHub / Gitee 授权
        ↓
④ OAuth 回调
        ↓
⑤ ★ 判断：这个 provider 身份【绑定过账号】吗？
        ├── ✅ 绑定过 ⇒ ★ 【登录】（★ 只查 login_open）
        └── ❌ 没绑定 ⇒ ★★ 【注册】（★ 必须查 registration_open + 邀请码）
                          ⇒ 建账号 + 绑定身份 + ★ 记 invited_by + ★ 核销邀请码
```

★ **两个入口，一个校验点**：★ 无论从哪进，

> ★★ **「首次建立账号」这一步，必须过邀请校验。**

#### ★★ 三条纪律

| # | 纪律 | 为什么 |
|---|---|---|
| **1** ★★ | ★ **邀请码在校验通过前不消耗** | ⚠ 用户授权失败 / 中途退出，**不能白白扣掉一个码** |
| **2** ★★ | ★ **核销必须与「建账号」在同一个事务里** | ⚠ 否则会出现"码被用了、账号没建成"（★ 用户拿不到账号，码也没了） |
| **3** ★★ | ★ **`registration_open = false` 时，OAuth 新用户一律拒绝** | ★ 且给出**可读原因**：★「本站当前**仅限邀请注册**，请向站长索取邀请码」 |

### U7.1 ★★ 先立一条铁律：勋章衡量「生产」，不衡量「消费」

★★ **这是本节最重要的一句**：

> 微信读书的勋章衡量的是「**你消耗了多少**」（读完 30 本、连续 180 天）。
> ⚠ **那套度量直接搬过来会变成刷量** ——
> 「你读了 5000 个函数」**不等于读懂**，而且 ★ **它可以用脚本刷**。

⇒ ★★ **本平台的勋章必须衡量「你留下了什么」与「你真正搞懂了什么」**，❌ 不是"你点了多少下"。

★★ **用户已把这条明确下来**（「**勋章我主要是为了鼓励生产，而不是用户阅读**」）——
★ 因此本章的判据**不是**"哪个更容易上"，★★ **而是"哪个更能让创作者愿意再发一篇"**。

⚠ 这有**明文依据**：`backend-design.md` §2.3.15 已禁止「**把停留时长当正向信号**」
（理由：代码场景里"**卡住**"是**负向**信号 —— 停得久说明看不懂，不是学得好）。

| 度量 | 用不用 | 为什么 |
|---|---|---|
| 写了多少条解释 / **被采纳**多少 | ✅★ | ★ 直接等于核心价值（知识沉淀）；★ 且**难刷**（要点得对，还要别人认） |
| 有多少人**读过**你的解释 | ✅★ | ★ **需要别人配合** ⇒ 天然抗刷 |
| 完成了几条**阅读路径** | ✅ | 有始有终 |
| 打开了多少**新语言 / 新项目** | ✅ | 衡量**广度**，❌ 不衡量次数 |
| 停留时长 / 点击次数 / 滚动深度 | ❌★ | **明文禁止**；且**必然催生刷量脚本** |
| 纯"登录天数"签到 | ❌ | 与"读懂代码"无关 ⇒ 是**虚假成就感** |

### U7.7 ⚠ 一个必须现在想清楚的问题：**依赖顺序**

> ★ **UGC（解释 / 阅读路径）还没做，而贡献类与荣誉类勋章【全部依赖它】。**

⇒ ★ **依赖顺序（已按 `B134`「鼓励生产」重排）**：

| 阶段 | 上什么 |
|---|---|
| **一期** | ★★ 把 `Achievement` / `UserAchievement` 表结构与分类**定下来并落表**<br>★★ **上「发布类」** —— ★ ✅ **不依赖 UGC**，且★★ **正是"鼓励生产"最直接的落点**<br>★ 例：第一次发布项目 · 发布 3 个项目 · **你的项目被 100 人读过** |
| **UGC 上线后** | ★★ 开**知识类** —— ★ **这是主体**（用户要的"鼓励生产"，**最重的产出是解释**） |
| **有规模后** | 开**荣誉类**（需要"别人"的基数） |
| ⚠ **不单独设阶段** | ~~探索类~~ —— ★ 降为"记录"，❌ **不进勋章体系**（`B134`） |

★★ **一个必须记住的排序**：

```
★ 发布项目（入口） → 写解释（主体） → 别人认可（荣誉）
   ↑ 一期就能做        ↑ UGC 上线后      ↑ 有规模后
```

⚠ **反过来做（先上荣誉类）会失败**：★ 荣誉类需要"**别人**"的基数，
★ 而平台上**还没有内容**时，**没有人会去关注任何人**。

★★ **为什么坚持"一开始只上几枚真的"**：
> ★ **勋章墙从第一天起就必须是真的** ——
> ⚠ 一个**空壳勋章墙**（全是"未解锁"）不会激励任何人，只会让人觉得"这平台没什么人"。

### U7.8 ★★★ 比勋章更有效的，是「**被看见**」

⇒ ★★ **建议：「创作数据反馈」与勋章并列为一等公民** —— ★ 而且它 **⭐ 一期就能做**。

## U8 ★★ 学习进度与「督促」

> **来源**：用户原话（2026-09-19 · `B135`）——
> 「我这是**代码学习平台**，学习者应该能**看见学习进度**之类的，**有目标，有进度**，
> **背后推一把，给点小压力，也可以**，整个**打卡**什么的，能够**督促学习**，
> ⚠ **但不给过强的学习压力**。」
>
> ⚠ **本节与 U7 的关系必须先说清** —— 否则会做成**两套互相打架**的东西。

---

### U8.1 ★★ 第一件事：把「勋章」与「学习进度」拆开

⚠ 直觉会把它们混成一个"激励模块"，★ **但它们的目的、可见性、规则完全不同**：

| | **成就 / 勋章**（U7） | ★★ **学习进度**（本节） |
|---|---|---|
| **服务谁** | ★ **创作者**（鼓励**生产**） | ★ **学习者**（帮助**坚持**） |
| **本质** | ★ **荣誉**（对外展示） | ★ **工具**（给自己看） |
| **是否公开** | ★ **公开**（徽章墙 · 署名旁） | ⚠ ★★ **私有**（只有你自己看得到） |
| **要不要防刷** | ⚠ ★★ **必须防**（公开 ⇒ 可比 ⇒ 一定有人刷） | ✅ **无所谓**（刷了只骗自己） |
| **断掉什么后果** | 不适用 | ★ **零成本**（进度**永远不会归零**） |
| **能不能有压力** | ⚠ **不能**（公开制造压力 ⇒ 焦虑 / 军备竞赛） | ★ **可以有温和的督促** |

★★★ **这条推论是本节的钥匙**：

> ★★ **因为「学习进度」是【私有】的，所以它不必防刷；**
> ★★ **因为「勋章」是【公开】的，所以它必须防刷。**
> ⇒ ★ **两套设计原则不同，❌ 不要用一套规则管两者。**

★ 于是"**打卡该放哪**"也自然清楚了：

| | |
|---|---|
| ★ **打卡属于「学习进度」侧**（私有、给自己看） | ✅ **可以带一点督促** |
| ❌ **不做成公开勋章** | ⚠ 否则立刻变成排行榜与焦虑 —— 即 `U7.5` 第 **4 / 5 / 6** 条禁止的东西 |

---

### U8.2 ★★ 「督促」与「压迫」的界线（★ 五条判据）

★★ 用户说「**给点小压力，也可以，但不给过强的学习压力**」——
★ 那就必须把这条线**画得非常具体**，否则实现时一定会滑过去。

| # | 维度 | ✅ **督促**（健康） | ❌ **压迫**（有害） |
|---|---|---|---|
| **1** | **参照系** | ★ **与自己的过去比**（上周 3 步，本周 5 步） | ⚠ **与别人比**（排行榜、"好友超越了你"） |
| **2** | **目标来源** | ★ **自己设的**（"我要读完这个项目"） | ⚠ **平台派的**（"你本月应完成 5 个"） |
| **3** | **失败的后果** | ★ **只是"没做完"** —— 进度停在那儿，随时能继续 | ⚠ **有惩罚感** —— 连续中断**归零**、掉等级 |
| **4** | **提醒方式** | ★ **被动可见**（打开就能看到） | ⚠ **主动催促**（推送 / 红点 / "该学习了"） |
| **5** | **复位的代价** | ★ **零**（中断一个月回来，进度还在） | ⚠ **牺牲已有成果**（清零、降级） |

★★★ **一句话判据**：

> **压力应当来自「我自己还没做完」，❌ 不应来自「别人比我强 / 平台在罚我」。**

★★★ **以及一条必须写死的硬判据**：

> ★★ **任何"中断即归零"的设计，都直接违反「不给过强的学习压力」。**
> ⚠ 因为**归零会让用户不敢回来** —— ★ **而这恰恰是最糟的结果**：
> ★ 平台真正需要的是"**他中断了，但还会回来**"，❌ 不是"他一天都不敢断"。

### U8.3 ★ 打卡：记「**学过**」，❌ 不记「**来过**」

⚠ 这一条**修正 `U7.5` 第 3 条的口径**（那里的禁止**仍然成立**，只是边界要写清）：

| | ✅ **可以做** | ❌ **不能做** |
|---|---|---|
| **打卡记什么** | ★ **"今天看懂了什么"** —— 走过 N 个节点 / 写下 1 条笔记 / 走完 1 步阅读路径 | ⚠ **"今天登录了"**（与"读懂代码"无关 ⇒ `U7.5` 第 3 条禁的**就是它**） |
| **断签的后果** | ★ **只是这条线断了**，★★ **进度完全不清零** | ⚠ **连续记录归零 / 任何形式的惩罚** |
| **展示方式** | ★ **"本周学了 3 天"** | ⚠ **"你已断签 5 天"** |

★★ **一个很小、但效果差很远的设计 —— 断签之后的那句文案**：

| | 文案 |
|---|---|
| ✅ | 「**欢迎回来，上次看到 `parse_packet()` 的第 3 步**」 |
| ❌ | 「你已断签 5 天」 |

> ★ **这句话决定了用户断签之后"敢不敢回来"。**
> ⚠ 而这正是"不给过强压力"要保护的东西。

★ **附带一条**：★ **不做"连续 30 天"这种长链** —— 改成 **"本周 N 天"**。

| | 理由 |
|---|---|
| ⚠ **长链** | 一旦断掉，**心理代价巨大**（30 天积累一夜归零）⇒ ★ **那正是"过强的压力"** |
| ★ **短周期** | ★ **天然复位** —— 「本周 3 天」**没有"断"这个概念** |

### U8.4 ★★ 学习进度数据从哪来（⚠ 一个必须现在决定的取舍）

★ 要让学习者看见"**我走过这个项目的哪些部分**"，需要一份 **用户 × 节点** 的访问记录。

| 方案 | 评价 |
|---|---|
| ★ **服务端记** | ✅ 换设备**不丢**（而"进度"最怕丢） · ⚠ 需要一张新表 + 高频写入 |
| ⚠ 只记在浏览器本地 | ✅ 零服务端成本 · ⚠ ★ **换电脑就没了** —— 对"进度"是**致命伤** |

⇒ ★ **建议：服务端记**，⚠ 但**必须守三条隐私纪律**：

| # | 纪律 |
|---|---|
| **1** | ★★ **只记「进度」，❌ 不记「轨迹」** —— 存 `(用户, 项目, 已走过的节点数, 最后一步, 更新时间)`；⚠ **不存完整的访问时间线、不记停留时长** |
| **2** | ★★ **只给用户自己看** —— ❌ 不对外公开、❌ 不进任何对外接口、❌ 不做用户画像 |
| **3** | ★ 登出 / 删除账号时**一并删除**（`backend-data-lifecycle.md`：账号主体数据"**删除或匿名化**"） |

★ **为什么"够用"**：进度只需要回答三个问题 ——
**① 我走到哪了 ② 我还没看哪些 ③ 怎么接着上次继续**。
⚠ 这三件事**都不需要知道"我在哪个节点停了 47 秒"**。

## U9 ★★ 付费项目与权益槽位

> **来源**：用户原话（2026-09-19 · `B136`）——
> 「接下来，**CSDN 有付费阅读模式，我十分讨厌这种模式**，但这对**吸引创作**是有利的，
> **知识应该共享，但现在社会需要钱**。所以，我决定**限制普通用户和 VIP 用户能做付费项目的数量**，
> **由管理员统一控制，可以调节**。比如你交了多少钱，我给你开一个**付费槽位**。
> 不过，**这是以后，用户多了点收费设计**。**前期，主要就是告诉管理员，然后管理员开一个槽位**。」

---

### U9.1 ★★ 先处理一处**直接冲突**（不处理，文档会自相矛盾）

⚠ `U1` 立了一条铁律：**公开版的「读」对所有登录用户永远平等**，VIP 只卖配额、❌ 不卖内容。

★★ **而"付费项目"就是内容特权** —— ★ **这是正面冲突，必须显式化解**，❌ 不能装看不见。

#### ★★★ 化解方式：把本平台与 CSDN 的**三个区别**写死

| # | 维度 | ❌ **CSDN 模式**（★ 用户讨厌的） | ✅ **本平台** |
|---|---|---|---|
| **1** | **谁定价** | ⚠ **平台**把内容锁起来卖 | ★★ **作者自己**决定要不要收、收多少 |
| **2** | **锁的是什么** | ⚠ **代码 / 别人的文章**（本已公开的东西被搬进来锁上） | ★★ **作者自己写的「讲解」** —— ★ **代码仍在 GitHub 上公开** |
| **3** | **不付钱的后果** | ⚠ **什么都看不了**（连目录都不给） | ★★ **仍然能自己读代码**（★ **图与结构免费**）—— 只是**没人带** |

★★★ **一句话把区别说清**：

> **本平台不卖代码，卖的是「读懂它的路径」。**
> ★ **代码永远在 GitHub 上，谁也锁不住** ——
> ★★ 所以付费**不会让知识消失**，它只是让「**有人带你读**」这件事需要付费。
>
> ★ 这正是它与 CSDN 的**根本区别**：★ **CSDN 把公开的东西锁起来；本平台不锁任何公开的东西。**

★ 而且这个区别**有天然保障**：★★ **源码在用户自己的仓库里，平台锁不住** ——
⚠ 一旦有人试图"锁代码"，**技术上做不到**，❌ 不需要靠自觉。

---

### U9.2 ★★ 边界：**能锁什么 / 不能锁什么**（★ 硬约束）

#### ★★★ 先立**原则**（`B139` · ★ 用户的完整表述）

> **用户原话**：
> 「我管的是**作者在本站写的收费解释文字和阅读路径推荐**，这是付费的。
> 其他的 **B站视频链接和 CSDN 链接**这些，**我不管，不能把他作为收费的部分，
> 要放到附录，让大家不管怎么样都能看到**。
> ★★ **我不能在这些免费内容上，再加一层收费** —— 这样**有法律问题**，
> 而且**也违背了我共享知识的理念**。」

★★★ **这条表述比"列举能锁什么"好得多** —— ★ 它是一条**原则**，不是一个清单：

> ★★★ **付费的正当性，只来自「作者创造了他原本不存在的讲解」。**
> ★ **不来自「他把别人已经公开的东西挪了个位置」。**

★ **两个理由指向同一个结论**：

| # | 理由 | 解释 |
|---|---|---|
| **1** ★★ | **有法律问题** | ★★ **你不能对「不属于你的东西」设收费门槛** —— 这是**权利的边界**，不是平台的规则。<br>★ B 站视频的著作权属于 UP 主、CSDN 文章属于作者 ⇒ ★ **把"访问他人作品"打包进自己的付费内容** = **拿别人的作品牟利**（⚠ 不当得利 / 信息网络传播权风险）<br>⚠ 且**平台也会被牵连**（★ 避风港要求平台**不从侵权中获利**） |
| **2** ★★ | **违背共享理念** | ★ 外部链接指向的**正是已经在共享的东西**（B 站视频公开、CSDN 文章公开）<br>⇒ ★★ **把公开的东西锁起来，既违法又违心** |

★ 所以"要不要收"的判据**只有一个**：

> ★★ **这份内容里，有多少是作者自己新写的？**

⚠ 而且由此**再推出一条**（★ 很有用，且好执行）：

> ★★ **收费文字必须「自身可读」** —— ★ 它必须**自己把东西讲清了**，
> ❌ **不能只是一句"去看链接"**。
> ★ 理由：★ **一条只指向别处、自己不讲东西的文字，没有新增任何智力劳动** ⇒ ★ **不具备收费的正当性**。

#### 由原则推出的结果

| | 内容 | 能否付费 |
|---|---|---|
| ❌ **不能锁** | ★ **代码本身** | ⚠ 它在 **GitHub 上公开** —— ★ **锁不住，也没道理** |
| ❌ **不能锁** | ★ **图与结构**（节点 / 边 / 调用链 / **多跳邻域**） | ★ **这是"自己读代码"的基础设施** —— ⚠ 锁了它，**不付钱的人连自己读都不行了**（★ **那比 CSDN 还糟**） |
| ❌ **不能锁** | ★ **别人写的解释 / 阅读路径** | ⚠ 那是**别人的**产出，❌ 你无权收费 |
| ❌ **不能锁** | ★ **外部平台内容**（B 站视频 / CSDN 文章） | ⚠ **那是别人的内容** —— ★ 收费会**直接触发侵权**（见 `backend-design.md` M 节） |
| ✅ **可以锁** | ★★ **作者自己写的**：**深度解释 · 阅读路径 · 逐行讲解** | ★ **这是作者的智力产出** —— ★ 收费**只允许对这一类** |

★ **阅读路径怎么切**（⚠ 容易混，写清）：★ 按 `U9.5`「**摘要永远公开**」——

| 部分 | 收费吗 |
|---|---|
| ★ **路径的「目录」**（有几步、每步讲哪个函数） | ❌ **免费** |
| ★ **每步的讲解正文** | ✅ **付费** |

★ 即：★ **「带你看哪」免费，「怎么看你懂了」付费。**

★★ **一句话**：★ **锁「讲解」，❌ 不锁「结构」。**

> ★ **为什么这条必须写成硬约束**：★ 因为它是**唯一能保证"不付钱的人仍能自己学"**的东西 ——
> ⚠ 一旦允许锁图，本平台**立刻比 CSDN 更糟**（★ CSDN 至少让你看目录）。

★ 正确做法：

| 位置 | 放什么 |

| **正文** | ★ 保留**引用标记**（如「详见 **附录 A-1**」） |
| **附录** | ★ **完整链接 + 署名三要素**（`source_platform` / `author` / `source_url`） |

⇒ ★ **形式上分离，语义上仍然连着。**

**修正 ②：★★ 不要新造结构 —— 复用契约 §20.5 的「媒体卡片」**

★ `frontend-contract.md` **§20.5 已经有一整套**（`GET …/media/?anchor_id=` + 写接口），
且**六条硬要求都写好了**：

| 已有要求（§20.5） | 说明 |
|---|---|
| `embed_allowed` **一期恒 false** | ★ **只渲染跳转卡**（❌ 不做站内播放 —— ★ 理由不是带宽，是**法律与共赢**） |
| ★ **署名三字段必须可见** | `source_platform` / `author` / `source_url` —— ❌ 不得隐藏、不得折叠 |
| ★ **不复制正文** | 文章类**只显示 `note`（作者自写一句话）**，❌ 不得拉取原文摘要 |

#### ✅ 边界修正（`B138` · ★ 用户纠正了我的方向）

★★ **用户指出我上一轮防错了对象**，而且**他是对的**：

> 「附录只放外部链接，你这个**有什么用**。**作者把讲解做成链接放在附录就放呗，
> 他自己脑子抽了，自己绕过来能收钱的地方，是他自己不要钱的事，我不管。**
> ★★ **我只管：另一个作者把其他作者的链接加入目录，从而绕过，让别的作者亏钱。**」

★★★ **两处修正**：

| # | 我上一轮写的 | ★ 修正后 |
|---|---|---|
| **1** | ⚠ 防「**作者自己绕过付费**」 | ❌ **删掉** —— ★ **作者绕过自己 = 他自己不要钱**，⚠ **平台没有义务替他着急**；★ 那是**管错了对象** |
| **2** | ⚠ 限制「**附录只放外部链接**」 | ❌ **也删掉** —— ★ 理由见下（★ **链接根本不承载内容**） |

##### ★★★ 一个更根本的澄清：**"链接"本身不承载内容**

★★ **链接只是一串网址** —— ★ **读者点过去看到的，是【原平台】的内容**：

| 东西 | 有没有"被绕过"的风险 |
|---|---|
| ★ **链接（URL）** | ❌ **几乎没有** —— ★ 点过去看到的是**原平台**的东西 ⇒ ★ **搬来搬去不产生任何信息** |
| ★★ **文字**（他人付费解释里的句子） | ⚠★ **有** —— ★★ **这才是真正能让人亏钱的东西** |

★ 所以：★★ **单纯搬链接，其实伤不到任何人** ——
★ 因为 ★ **他自己公开在 B 站的视频，谁都能找到；他自己藏起来的，你搬链接也没用**。

##### ★★ 那么真正要防的是什么：**「转述」**

★★ 用户要的这条规则，**准确的表述**应当是：

> ★★ **不能在【免费内容】里，把【他人付费内容】里的「文字」转述出来。**
> ★ 这不是"绕过链接" —— ★★ **这是"绕过人"。**

★ **三条可执行判据**：

| # | 判据 | 说明 |
|---|---|---|
| **1** ★★ | ★ **不得"逐条对应"** | ⚠ 若 A 的免费内容与 B 的付费内容**步骤一一对应**（B 的第 1/2/3 步 ↔ A 的第 1/2/3 步）⇒ ★ **视为转述** |
| **2** ★★ | ★ **不得"转手付费墙后的外链"** | ★ 区别很细、但很准：**"他自己公开在主页上的链接"** ≠ **"他特意放在付费内容里的链接"**；⚠ 搬后者 = ★ **把人家选择"收费才给"的东西拿出来了** |
| **3** ★★ | ★ **阅读路径不得"实质替代"** | ⚠ 一条**免费**路径若**覆盖了**另一条**付费**路径的相同内容 ⇒ ★ **视为绕过** |

##### ★ 执行手段（★ 判据需要人来判 —— 这才是关键）

★ 这三条**都需要人判断**，❌ 不能靠自动检测 ⇒ ★ 靠的是**已有的机制**：

| 手段 | 出处 |
|---|---|
| ★ **举报入口**（当事人举报） | ★ 契约 §20 已有「**删除入口 + 可申诉**」 |
| ★ **管理员裁决** | ★ 与"**付费槽位审核**"是**同一批人**（`U2.5`） |
| ★★ **审计留痕**（谁举报、谁裁决、依据哪一条） | ★ `AuditLog`（`U2.5` 纪律 1） |
| ★ **通知-删除 SLA 24h** | ★ `backend-design.md` 已有 |

★★ **语气很重要**：★ **先联系当事人、给改正机会**，❌ 不直接下架 ——
★★ 因为「**转述**」与「**正常引用**」的界线**本来就模糊**，⚠ **误杀比放过更伤人**。

#### ★★★ 顺着这个思路，可以得到一条**比"列举"更简洁的判据**

★ 用户这个建议的真正价值，是它**逼出了"付费边界"的本质**：

| 内容在哪 | 能不能收费 |
|---|---|
| ★ **在外部平台**（B 站视频 / CSDN 文章） | ❌ **不能** —— ★ **不是你的场地，也不是你独占的内容** |
| ★ **在本站、作者自己写的文字** | ✅ **可以** |
| ★ **在本站、平台产出的结构**（图 / 节点 / 调用链） | ❌ **不能** —— ★ 那是"自己读代码"的基础设施（`U9.2`） |
| ★ **在本站、别人写的文字** | ❌ **不能** |

★★★ **一句话**：

> **付费的边界 = 「作者在本站写下的文字」。**
> ★ 出了这个圈（**外部内容 / 平台结构 / 别人的东西**）—— ★ **一律免费**。

★ 这比"列举能锁什么"**更简洁，而且可判定**（★ **只看内容在哪**）。

### U9.9 ★★ 读者举报 · 众包发现 · 二次收费

> **用户原话（`B140`）**：
> 「**设置读者举报**，以后用户多了，**管理员挨个检查不完的，发动群众最好**。
> ★★ 也解决：**本来就是收费 CSDN 文章，这里再收费 —— 一个解释，赚两份钱，违背我共享知识原则**。」

#### ① ★★ 为什么必须靠群众：**规模上，管理员审不完**

★★ 用户的判断是对的，而且这是**结构性的**：

| | 说明 |
|---|---|
| ★ **付费项目数** | ★ 一期靠**槽位限制**（`U9.3`）⇒ ★ **数量可控** |
| ⚠ **付费内容条数** | ⚠ 每个项目下有**几十上百条解释** ⇒ ★ **逐条审核在数学上不可行** |
| ★★ **但"有问题的永远是少数"** | ★ 绝大多数作者不会乱来 ⇒ ★★ **让多数人发现少数问题**，成本远低于**全量审核** |

#### ② ⚠ 但「发动群众」有一条**红线**（★ 不写清会变成网络暴力）

⚠ **反模式**：**"举报满 N 次自动下架"** ——
★ 后果：⚠ 有人为了**免费看内容**，组织恶意举报 ⇒ ★ **作者被误杀**。

★★★ **正确的分工**：

| 谁 | 负责 | 为什么 |
|---|---|---|
| ★★ **群众** | ★ **发现**问题 | ★ 规模问题**只有群众能解决** |
| ★★ **管理员** | ★ **裁决**问题 | ★ 判断需要**人和责任** ⇒ ★ ❌ **不众包裁决** |

⇒ ★★ **举报的作用是「标记 + 通知作者」，❌ 不是「自动下架」。**

| 举报之后 | 做什么 |
|---|---|
| ★ **→ 作者** | ★ 先**通知作者**，给改正机会（★ 与 `U9.7` 语气一致：**误杀比放过更伤人**） |
| ★★ **→ 管理员** | ★ 只把**"被举报多次 / 多人举报"**的挑出来 ⇒ ★★ **管理员的清单从"全部内容"缩到"争议内容"** ✅ |

#### ③ ★★ 举报必须**指定理由**（★ 理由 = `U9.2` / `U9.7` 的那几条判据）

⚠ 不能只有一个"举报"按钮 —— ★ 那样既无法统计，也无法让作者知道要改什么。

| 举报理由（下拉选） | ★ 对应判据 |
|---|---|
| ★ **正文其实没内容**（只有一两句话 / 只指向链接） | `U9.2`「**收费文字必须自身可读**」 |
| ★ **内容是搬运他人的付费内容**（逐条对应） | `U9.7` 判据 1 |
| ★ **内容里含他人的付费外链**（转手付费墙后的链接） | `U9.7` 判据 2 |
| ★★ **二次收费** | ★ 见本节 ④ |
| ★ **外部链接没标注收费状态** | ★ 见本节 ⑤ |

#### ④ ★★★ 二次收费：**用户发现的第三种滥用**

★★ **用户指出的情形**：★ **本来就是收费的 CSDN 文章，搬到本站再收一次费** ——
★★ **一个解释，赚两份钱。**

★ 但要**分成两种情形**，⚠ 处理完全不同：

| 情形 | 判定 | 处理 |
|---|---|---|
| ★★ **A. 把 CSDN 付费文章的内容搬来本站再收费** | ⚠★ **违反 `B139` 原则** —— ★ **那不是"新写的"** | ✅ **禁止** —— ★ 举报 + 管理员裁决 |
| ★★ **B. 本站写了新解释，附录链到自己的 CSDN 付费文章** | ★ **本身不违规**（★ 新解释确实是他写的） | ⚠ **但必须标注**（见 ⑤） |

★★★ **判 A 的关键**：

> ★ **不是"他有没有在别处收费"，而是「本站这段文字是不是新写的」。**
> ★ 若是**同一份劳动卖两次** ⇒ ★ **违规**；
> ★ 若是**两份不同的劳动** ⇒ ✅ **允许**。

#### ⑤ ★★ 由此补一条规则：**附录里的外部链接必须标注收费状态**

| 标注 | 什么时候用 |
|---|---|
| ★ `免费` | 点过去就能看 |
| ★★ `需要付费` | ★ 该平台 / 该文章收费 |
| ★ `需要登录` | 需注册账号 |

★★ **这条规则一次服务两个目的**（★ 很划算）：

| # | 目的 |

★ 再加上 ③ 的**举报理由** ⇒ ★ **作者、读者、管理员三方都能看见同一件事**。

### U6.1 ★★ 用户存储空间（`B152` · 2026-09-19）

> **用户原话**：「要设立一个**用户存储空间**，用来放用户的源码项目，
> 要是**源码太大，占了太多空间，就不好了**。这样也可以**间接限制图数据的大小**。
> 这也可以是 **VIP 用户的存储空间更大的具体体现**。」

★★ 这个设计**同时解决三件事**：

| # | 解决了什么 |
|---|---|
| **1** | ★ **磁盘不会被打爆** —— ★ **每个用户自己**的配额，⚠ 而不是全站共用一个池子（★ 那样一个人就能拖垮所有人） |
| **2** | ★★ **间接限制图数据大小** —— ★ 图来自源码，★ 源码就那么多，图不可能无限大 |
| **3** | ★★★ **VIP 的"更大"有了具体形态** —— ★ 符合 `U1` 铁律：**只是额度更大，❌ 不是能看更多** |

★ 落地：`{ASTROLABE_STORAGE_ROOT}/{project_ref}/`，
路径**只能由 `project_ref` 派生**（★ 形态 `proj_[0-9a-f]{32}` ⇒ ★ **结构上不可穿越**）。
★★ **调用方再也传不进任意路径** —— ⚠ 这一点还顺带堵掉了"让服务端读容器里任何目录"的隐患。

★★★ **两道闸门 + 一条待办**：

| # | 在哪 | 能判断什么 |
|---|---|---|
| **1** | 发布时（`publish.publish_project`） | ★ **用户已经满了** ⇒ 立刻拒绝（❌ 别让他等半天才失败） |
| **2** | 采集时（`storage.ingest`，作业里） | ★★ **边写边数，超了立即中止并清理**（⚠ 不留半个仓库） |
| **3** | ✅ **已落地**（`B153`）：用**归属校验那次请求已经拿到的 `repo.size`** 预判 | ★★ **零额外请求**（⚠ 不是再发一次 API）；★ 保守系数 **0.8**（★ 因为 `size` 含 `.git` 而我们跳过它 ⇒ 真实值通常更小，★★ **宁可放过、不要误杀**） |
| **3b** | ✅ 落地在拉取**解压时**（`fetch.fetch_archive`） | ★★ **边下边解边计数，超了立即中止并清理** —— ⚠★ 这是**唯一**能防"解压炸弹"的办法（❌ 看成员声明的 `size` 没用，那是**攻击者写的**） |
