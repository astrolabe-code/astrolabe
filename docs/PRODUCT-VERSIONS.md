# 产品分版与许可策略

> **本文的地位**：三版定位、交付边界、许可策略的**现行依据**。
> **写作时间**：2026-09-19
> ⚠ **本文涉及法律的部分，均为「行业惯例层面的判断」，不构成法律结论** —— 正式条款与许可证选型**发布前需经一次法务确认**。

---

## A 三版定位

| 版本 | 面向谁 | 部署在哪 | 谁运营 | 核心价值 |
|---|---|---|---|---|
| **公开版** | 大众学习者 | **互联网（仅此一个实例）** | 你本人 | ★ **社交 + 知识沉淀**（1000 人读同一项目 = 1 张图 + 1000 份解释） |
| **个人版** | 单个开发者 | ★ **本地**（本机） | 用户自己 | ★ **带图节点的笔记**（笔记钉在代码位置上） |
| **企业版** | 公司 | ★ **客户自有内网** | 客户 | 内网代码图谱 + 团队协作；★ **由你授权**，不是卖源码 |

## B 各版「能做什么 / 明确禁止什么」

### B1 公开版

| | 内容 |
|---|---|
| **能** | ★ **任何人（含游客）都能浏览公开项目**；★ 登录后可写解释 / 提问 / 阅读路径<br>★ **付费项目**（`B136`–`B140`）：★ **只有「作者在本站写的讲解文字 + 阅读路径」可收费**；⚠ **图 / 结构 / 外部链接一律免费** —— 详见 `USERS-AND-AUTH.md` U9<br>⚠ **注册受邀请制约束**（`B141`）：★ **读不需要账号，写需要** |
| **源码来源** | ★ **只能由服务端从 GitHub / Gitee 拉取**（`B109`）；⚠ **用户上传的 zip 一律不公开** |
| ★ **禁止** | 私有源码上行；上传源码包创建公开项目（★ 唯一例外 = 管理员特批） |

### B2 个人版

| | 内容 |
|---|---|
| **能** | ★ **本地解析自己的代码**（含公司私有代码）、写带图笔记、导出 `.webapkg` |
| ★ **禁止** | ⚠ **私有源码永不上行** —— 个人版的数据**只在本机** |

### B3 企业版

| | 内容 |
|---|---|
| **能** | 在公司**内网**部署，供**本公司员工**使用；可上传 zip（★ 源码版权由客户自负） |
| ★ **禁止** | ⚠ **不得部署到公网**（互联网）对外提供服务；不得再分发；不得去除署名与品牌 |
| ★ **交付方式** | **授权部署**，非源码销售 —— ⚠ 具体交付物见 C 节 |

## C ★ 仓库边界：公开什么 / 私有什么

| | 放在**公开仓库**（GitHub，任何人可见） | 放在**私有保管**（不公开） |
|---|---|---|
| **内容** | 解析器 · 图模型 · 锚定层 · `.webapkg` 格式 · 开放 API 契约 | ★ **部署脚本** · 运维工具 · **企业版功能**（SSO / 审计 / 多租户）· 交接手册 |
| **理由** | 这些是「**标准**」，公开才能成为事实标准（`S2.1`） | ★ 这些是「**产品**」与「**可交接材料**」（`S2.2` / `S7`） |
| **谁能拿到** | 所有人 | 授权客户 / 签约接盘方 |

> ★ **"不放部署脚本"能抬高门槛，但挡不住会写的人** —— 真正的防线在 D 节（许可证）与商标。

## D ★★ 许可策略

### D1 诉求（用户原话，作为判据）

> **可看、可学，但不可商用** —— 也就是**不能拿这套源码部署、公开到互联网上**；
> 还让我看见了，**我要能追究其法律责任、让其下架**。
> 别人在内网怎么部署，**我也不知道，也懒得去追究**。

⇒ 拆成四条硬要求：

| # | 要求 |
|---|---|
| **1** | ✅ 允许：**阅读、学习、研究** |
| **2** | ❌ 禁止：**商业使用** |
| **3** | ❌ 禁止：★ **部署到公网对外提供服务**（← 最关键的一条） |
| **4** | ★ **纯内网自用不追究**（不设防、不监控） |

### D2 候选许可证对比

| 许可证 | 可看 / 可学 | 商用 | ★ 部署到公网 | 是否 OSI 开源 | 贴合度 |
|---|---|---|---|---|---|
| MIT / Apache-2.0 | ✅ | ✅ | ✅ | ✅ | ❌ 完全不符 |
| GPL / AGPL | ✅ | ✅ | ✅（须开源衍生） | ✅ | ❌ 完全不符 |
| **PolyForm Noncommercial 1.0** | ✅ | ❌ | ⚠ **只禁"商业目的"** —— **免费搭个公开站可能不算违规** | ❌ | ⚠ 半符合 |
| ★ **PolyForm Strict 1.0** | ✅ | ❌ | ✅ **禁止几乎所有使用**（最严） | ❌ | ★★ **很符合** |
| ★ **Elastic License 2.0** | ✅ | ⚠ 允许内部自用，**禁止"作为托管服务提供给第三方"** | ✅ **明确禁止托管服务** | ❌ | ★★ **很符合** |
| BSL 1.1 | ✅ | ⚠ 禁生产使用 | ⚠ **到期后自动转为真开源**（通常 4 年） | ❌ | ⚠ 有"变开源"副作用 |
| Commons Clause + Apache | ✅ | ❌ | ⚠ **只禁"销售"，不禁免费公开部署** | ❌（有争议） | ⚠ 半符合 |
| SSPL | ✅ | ✅ | ⚠ 要求**开源整个服务栈** | ❌ | ❌ 不符 |
| 自己写条款 | ✅ | 你定 | 你定 | ❌ | ⚠ **措辞不当可能被认定无效** |

### D3 ★ 推荐方案：**限制性许可 + 商业授权（双轨）**

```
公开仓库 ── 限制性许可证（Elastic License 2.0 或 PolyForm Strict 1.0）
             ↑ 满足「可看、可学、禁商用、禁公网部署」
                    ↓
需要商用 / 内网部署的企业 ── ★ 单独签署商业授权（收费）
             ↑ 这正是「企业版」的商业模式（MySQL / Qt / MongoDB 同款）
```

★ **为什么推荐这两个**：

| 许可证 | 为什么 |
|---|---|
| **Elastic License 2.0** | ★ **明确禁止"作为托管服务提供给第三方"** —— 正对你的第 3 条；同时**允许企业内部自用** —— 正对你的第 4 条（内网不管） |
| **PolyForm Strict 1.0** | ★ 最严，**几乎只允许阅读** —— 若想最大化控制，选它 |

⚠ **不推荐 BSL**：它**约定年限后自动转为真开源**，届时"禁止公网部署"会**自动失效**。

### D4 ⚠ 风险提示（必须知道）

| # | 事实 |
|---|---|
| **1** | ★ **许可证一旦发布不可撤回**（`S2.4`）—— 选错要用四年去后悔 |
| **2** | ⚠ **限制性许可证不是"开源"** —— GitHub 会标"No license / 自定义"，有些公司会因此**禁止员工查看**（这可能是你想要的，但要知道） |
| **3** | ⚠ **执行力取决于你是否愿意追** —— 条款写得再严，**没人执行 = 没有威慑** |
| **4** | ★ 若**暂时不确定**：**先不发代码**，GitHub 上「无 LICENSE」= **默认保留所有权利**（最严格，且完全合法） |

## E ★ 维权渠道（"追究并让其下架"怎么做）

★ 关键认知：**维权不需要律师也能启动** —— 先走平台的投诉通道。

| # | 渠道 | 适用 | 成本 |
|---|---|---|---|
| **1** ★★ | **GitHub DMCA Takedown**（`github.com/contact/dmca`） | 别人**在 GitHub 上 fork / 重发**你的代码 | ✅ **免费，填表即可** |
| **2** ★ | **国内云厂商侵权投诉**（阿里云 / 腾讯云 / 华为云 均有入口） | 对方**用云服务器**跑你的代码 | 免费 |
| **3** | **工信部 / 网信办 举报** | 对方是**国内备案站点** | 免费 |
| **4** | **ICP 备案查询**（`beian.miit.gov.cn`） | ★ **先查到"是谁在运营"** —— 这是所有后续动作的前提 | 免费 |
| **5** | **律师函 / 起诉** | 对方拒不配合 | 花钱，**最后手段** |
| **6** ★ | **商标**（`S2.5` 工具一第 4 项） | ★ **投诉时最硬的抓手** —— "用了我的名字"比"用了我的代码"好证明得多 | 注册费 |

> ★ **建议顺序**：**先查备案找主体 → 平台投诉 → 商标兜底**。
> ⚠ 纯内网部署**你察觉不到、也无需处理**（D1 第 4 条）—— 这正是本策略**故意留的空间**。

## F 功能开关表（哪些企业功能将来可"收回"）

★ 目的：将来有平台支持时，把企业功能**收进公开版的付费层**（GitHub 模式）。

| 功能 | 一期 | 将来 |
|---|---|---|
| 多租户 / 组织 / 角色 / 配额 | ⚠ 一期不做（★ **但「能力表 + `tier` 字段」一期就要有** —— 见 `USERS-AND-AUTH.md` U5 / U6） | ★ 可收回进公开版付费层 |
| SSO / 目录同步 / 账号生命周期 | ❌ 不做 | ★ 同上 |
| 审计增强 / 合规报表 / 取证视图 | ❌ 不做 | ★ 同上 |
| 私有部署的运维工具 | ❌ 不做 | ★ 同上 |
| 白标 / 品牌定制 | ❌ 不做 | 保留 |

⚠ **前提**：★ **这些功能一期就要"可开可关"地设计**（`S4` 的功能开关思路），**别写死**。
⚠ **代价**：一旦授权企业版，★ **自托管版本要长期维护**（不能断供）—— 这是"GitHub 模式"的真实成本。

## G ★ 裁定：`S2.1` 第 10 项 —— **部署脚本不开源**

| | 原口径（`S2.1`） | ★ 新裁定（2026-09-19） |
|---|---|---|
| 单机自托管部署脚本 | **可以开源**（理由：可交接性） | ★ **不开源** —— 移入**私有保管** |
| 理由 | —— | ★ 用户明确要求「**其他人不得下载我的网站源码部署到公网上**」；且**企业版的核心价值 = 自托管能力**，开源等于送出去 |
| 可交接性怎么办 | —— | ★ **不冲突**：脚本**单独保管**，**签约接盘方时提供** |

## H 分期路线

```
第 1 步 ★ 内核：解析器 + 图模型 + 本地笔记（SQLite）
          ← 同时是【个人版的全部】【公开版的地基】【企业版的底座】
第 2 步   公开版：Django + PG + 多用户 + 社交 + 服务端拉源码解析
第 3 步   企业版：授权内网部署 + 企业功能（SSO / 审计 / 多租户）
第 4 步   条件成熟时：把企业功能收回，做公开版付费层（管理费 / 席位费）
```
