## 零、威胁模型与预期（先说清楚挡什么、不挡什么）

> 所有者原话（2026-11-04）：「我这只是为了挡一些**技术水平不高**的恶意用户。
> 要是有人**花钱雇人**去刷流量，就算是大网站都不一定扛得住，何况我这个小小网站呢？」

### 0.1 本方案挡的是谁

```
✅ 拿现成工具扫接口的（sqlmap / 爬虫框架 / 爆破脚本）
✅ 手写几行 requests 就想刷的
✅ 清 Cookie 换身份、反复重试的低成本投机者
✅ 一个脚本把队列塞满、把 CPU 吃光的"顺手作恶"
```

### 0.2 本方案**不**挡谁（要认清）

```
❌ 花钱雇人 / 买僵尸网络 / 打码平台流水线
❌ 有预算的定向攻击（分布式 IP、真人众包、GPU 算力）
❌ 链路层/带宽层攻击（那是 DDoS 防护/CDN 的事，要花钱，本方案不涉及）
❌ **换用户名爆破**（每个名字只试 5 次，但换名字继续试）
   ⇒ ★ 已决定接受（2026-11-04，见 10.5），兜底是"保命开关"
```

**原因很朴素**：一切应用层手段都是在"提高单次请求的成本"，
而对方愿意为单次请求付钱时，这个成本差就被抹平了。大站也一样。

### 0.3 所以设计目标是这四条（不是"防住所有攻击"）

```
① 让**技术水平不高**的人刷不动（成本 >> 收益）
② 让**正常用户完全感觉不到**（不误伤，这是小站最怕的）
③ 出事时**能定位**（谁在刷、刷什么、从哪来）
④ 出事时**能快速止血**（下面 0.4 的保命顺序）
```

### 0.4 真被打时的"保命顺序"（比限流更重要）

```
第 1 优先：数据不丢
  ⇒ 备份是每天 04:00 的，被打时不要动数据库；必要时先停写入口
  ⇒ ⚠ 备份 ≠ 能恢复：**每月做一次恢复演练**（建临时库 → 灌最新备份 → 比对行数 → 删库）
     否则"数据不丢"这一条是空的（2026-11-03 手工演练过一次，尚未自动化）

第 2 优先：站点活着（哪怕降级）
  ⇒ 维护模式：全站只读 / 只允许已登录用户 / 关闭解析与搜索
  ⇒ 静态页由 nginx 直接发，后端不参与 ⇒ 打得再狠也能打开一个"正在维护"页

第 3 优先：止血
  ⇒ 短封 + 关掉最贵的入口（解析、搜索、导出）
  ⇒ ★ **换用户名爆破 / 登录口被打** ⇒ 直接开「站点保护模式」
     （登录入口立刻只对 staff 开放 ⇒ 爆破连试密码的机会都没有；
       比临时加限流更快、更干净）

最后才是：花钱上 CDN / 清洗 / 换 IP
```

✅ **保命开关已实现（2026-11-04）**，两个入口等价：

```
后台  「站点参数」页顶部「站点保护模式」卡片 → 打开/关闭按钮（会留痕）
SSH   deploy/maintenance.sh on|off|status（admin 登不进来时用这个）
```

```
打开后：**已持有有效 session 的 admin** 一切正常，可在后台解除；
        未登录只能只读浏览；搜索 / 登录（非 staff）/ 写操作 一律 503；
        解析队列暂停领取新作业
        ⚠ 澄清（B9）：admin 若 session 已过期**也登不进来**（无 session 时无从判断是不是 staff）
          ⇒ 此时唯一解除路径是 SSH：`app/deploy/maintenance.sh off`
状态存放：data/uploads/.runtime/maintenance.flag（文件，不依赖 DB/Redis）
判定位置：web/middleware.ProtectModeMiddleware（先查 staff，再判只读/搜索）
⚠ 登录闸门放在 `authenticate()` **之前**：否则攻击者仍能用登录触发 PBKDF2，
   等于拿你的 CPU 当放大器
```

### 0.5 一句话

```
限流是"防小偷的门锁"，不是"防军队的城墙"。
门锁值得装（成本低、误伤小、挡住了绝大多数情况）；
城墙不要自己修（修不起，也不是这个站该操心的事）。
```

## 一、结论摘要（先看这段）

```
① 现在有 5 套限流/封禁机制，但其中 2 套**实际失效**：
   · 设备令牌发牌配额  → 退化成"全站 150/小时"（已实测打满）
   · IP 封禁          → 所有请求 IP 塌成网关，is_bannable 拒绝封它 ⇒ 完全无效
② 登录完全没有"失败次数"限制（只有审计记录）
③ 只有搜索接口被限流，写操作（发布/导出/删除）没有任何频率保护
④ 根本原因是**拿不到真实客户端 IP**；等自建隧道就绪后这些才能修对
⑤ 本方案不引入任何第三方服务（隐私优先），验证码**自己画**（Pillow）
⑥ 处置是层层递进的：429 → 蜜罐 → PoW → 图片验证码 → 短封（见第四、八、九节）
⑦ ⚠ **本方案只挡"技术水平不高的恶意用户"，不抗花钱雇人刷流量 / DDoS**（见第零节）
⑧ 本版已按审查意见修订：**IP 维度推迟到 P4、不做服务端 sleep、验证码 3 次、
   PoW 以"二进制位"为准、锁定检查在哈希之前**（详见附录 A）
```

### 2.2 两个失效点（有实测证据）

**① ~~M1 事实上是"全站 150/小时"~~ —— 已随令牌功能删除而消失（保留作历史）**

```
所有外部请求在 nginx 眼里都是同一个地址（宿主机 / 隧道那头）
⇒ "每 IP 150 张/小时" 变成 "全站 150 张/小时"

实测（2026-11-03）：
  astrolabe:dev:issue:127.0.0.1:498264 = 222   ← 已超过 150
  ⇒ 该小时内**新访客拿不到令牌**，全部落进 anon 共享桶（90 次/秒，所有人共用）
```

**② M3（IP 封禁）当前完全无效**

```
client_ip() 取 X-Real-IP = nginx 的 $remote_addr = 网关地址
is_bannable() 明确拒绝封 127.0.0.1 / 内网段（防自锁）
⇒ 后台「封禁」按钮点了不生效 —— 安全但无用
```

### 2.3 为什么 nginx 的限流被撤掉

```
撤除前：limit_conn / limit_req 按 $binary_remote_addr
但该地址是网关 ⇒ 实际是"全站总闸门"
表现：一个人刷，所有人一起被限（误伤式）
⇒ 撤除，把限速交给应用层按身份做（M2）
⇒ 等真实 IP 可用后，nginx 限流才有意义（见第十二节）
```

### 2.4 缺口

| 缺口 | 现状 | 严重度 |
|---|---|---|
| 登录无失败计数 | 只有 `login_fail` 审计，无锁定/延迟 | **高** |
| 写操作无限流 | 发布/导出/删除只有业务配额（3 次/天） | 中 |
| `anon` 桶全局共享 | 一个脚本占满，所有未登录用户受影响 | 中 |
| 固定窗口边界效应 | 第 59.9 秒 + 第 60.1 秒可各放一轮 | 低 |
| fail-open 未分级 | Redis 故障时一律放行（⚠ 限流可放，**登录计数/挑战不能放**，见 5.5） | 中 |

## 三、设计原则（借鉴大公司做法）

| 原则 | 含义 | 本方案的体现 |
|---|---|---|
| **① 身份优先，IP 兜底** | 有账号按账号算；IP 只用于匿名 | 登录用户完全不占 IP 额度 |
| **② 分层响应，不一步到位** | 429 → 蜜罐 → PoW → 图片验证码 → 短封，**不做永久封** | 第四 / 八 / 九节 |
| **③ 认证类数"失败"不数"频率"** | 限的是试错次数，不是访问次数 | 登录/注册 |
| **④ 按端点定政策** | 贵的接口严，便宜的不限 | 搜索/导出严，列表宽，静态不限 |
| **⑤ 挑战代替拒绝** | 可疑时要求"证明是真人"，而不是拉黑 | PoW（第八节）+ 图片验证码（第九节） |
| **⑥ 零第三方** | 访问者数据不出服务器 | 不用 Turnstile / reCAPTCHA |

> 为什么不用第三方验证：小站无法承担"用户 IP 与行为交给第三方"的隐私与合规风险。

## 四、目标架构（四层）

```
┌─ 第 0 层：静态资源 ────────────────────────────────┐
│  /app/*、/static/*   nginx 直接发，**不限流**       │
└────────────────────────────────────────────────────┘
┌─ 第 1 层：边缘（nginx，需要真实 IP）───────────────┐
│  连接数 / 请求速率  超限 → 429（不封）              │
└────────────────────────────────────────────────────┘
┌─ 第 2 层：身份（Django 中间件）────────────────────┐
│  按 u<id> / IP 分桶；搜索、写操作、导出各有额度     │
│  超限 → 429 + Retry-After；反复超限 → 要求 PoW      │
└────────────────────────────────────────────────────┘
┌─ 第 3 层：业务（视图/领域层）──────────────────────┐
│  配额（3 次/天、3 个项目）、队列（50 / 3）          │
└────────────────────────────────────────────────────┘
```

**一句话：nginx 挡"不是人的流量"，应用挡"是人但太快的"，配额挡"规则上限"。**

## 五、参数表（★ 标记处需所有者拍板）

### 5.1 读接口

| 接口 | 身份 | 额度 | 超限动作 |
|---|---|---|---|
| 静态资源 | — | 不限 | — |
| 列表 / 详情（普通读） | 登录 `u<id>` | ★ 30 次/秒 | 429 + `Retry-After` |
| | 匿名 按 IP | ★ 10 次/秒 | 429 + `Retry-After` |
| **搜索**（带 `q`） | 登录 `u<id>` | 10 次/秒（保持） | 429 + `Retry-After` |
| | 匿名 按 IP | ★ **5 次/秒**（可调） | 429 → 反复则 PoW / 验证码 |

⚠ 5 次/秒是按"一家人够用"定的**初值**；10 人办公室共享出口会碰到，上线后按 429 比例再调。

⚠★ **P4 之前不能启用这一行**（N1）：那时 `a<ip>` 就是网关地址，
   "每 IP 5 次/秒"实际是**全站匿名合计 5 次/秒** —— 日活几百的站高峰期会被自己打满。
   ⇒ 匿名分桶与收紧放到 **P2b-2（P4 之后）**；P2b-1 只收紧登录用户的额度。

### 5.2 写接口

| 接口 | 身份 | 额度 |
|---|---|---|
| 发布 / 删除 / 修改 | `u<id>` | ★ 30 次/分钟 |
| 导出 | `u<id>` | ★ **2 次/分钟**（原定 5 次；500 篇同步生成有内存峰值，见 5.6） |
| 提交解析 | `u<id>` | 保持 M4/M5（3 次/天、队列 3） |

### 5.3 认证接口（只数"失败"，不数"频率"）

| 维度 | 阈值 | 处置 |
|---|---|---|
| 同一**用户名**失败 | ★ 5 次 / 15 分钟 | 第 6 次起锁 15 分钟 → **返回 429 + `Retry-After: 900`**，⛔ 不在服务端 sleep |
| 同一 **IP** 失败 | ★ 20 次 / 15 分钟 | **P4 后：429 硬拒**；**P5 后：改为要求 PoW**（⚠ 现在 IP 是网关，本身不启用，见 A1） |
| 注册 | ★ 3 次 / 小时 / IP | 429 ｜ ⚠★ **P4 前不生效**：那时 IP 是网关，会变成"全站每小时 3 个"，直接卡死正常注册（不是"共享出口误伤"那么轻） |
| 成功登录 | — | **只清零"用户名"键；IP 键不清**（否则"错 19 次 + 成功 1 次"可永久洗白） |

⚠★ **三条硬性要求（漏一条就出洞）**：

```
① 用户名规范化：strip().lower()
   ⚠ 否则 Admin / admin 是两个键，直接绕过计数
② 不存在的用户名**同样**计数、同样锁定
   ⚠ 否则"被锁了 vs 密码错"就是免费的**用户名枚举 Oracle**
③ 锁定时的响应必须与"密码错误"**不可区分**（统一文案，⛔ 不写"该用户已锁定"）
```

⚠ 接受的风险（已决定，2026-11-04）：

```
① 知道用户名即可把别人锁 15 分钟（小站可接受；且不存在用户同样锁，不产生枚举信号）
② **换用户名爆破**：每个名字只给 5 次，但可以换名字继续试
   ⇒ ★ 接受，不做全站兜底（理由见 10.5；兜底手段是"保命开关"）
③ **锁定是硬等**：⛔ 不给"过图解锁"；解除只有两条路 ——
   等满 15 分钟，或管理员 SSH 跑 `unlock-login.sh <用户名>`（见 10.7）
   ⇒ admin 自己被反复锁时，同样用这条脚本解开（⛔ 不开免锁白名单）
```

### 5.4 封禁（人工，短封为主）

| 情形 | 时长 | 说明 |
|---|---|---|
| 首次确认滥用 | ★ 5 分钟 | 自动过期 |
| 同 IP 反复 | ★ 30 分钟 → 24 小时 | 递进 |
| 住宅 IP 上限 | ★ **24 小时** | 绝不能永久封（可能是一整个小区） |
| 机房 / 云 IP | 可 7 天 | 那里一般不是真人 |
| 登录用户 | 走**账号**处置 | 不动 IP |

### 5.5 Redis 故障时的策略（★ 必须分级，不能一律 fail-open）

| 类别 | 故障时 | 理由 |
|---|---|---|
| 限流（搜索 / 读写额度） | **fail-open** | 限流是保护措施，挂了不该让站点不可用 |
| 登录失败计数 / 锁定 | **fail-closed**：登录一律返回 **503「服务暂时不可用，请稍后再试」**，并记审计 `reason=redis_down` | fail-open 等于无限试密码；⛔ 不要伪装成"被锁定"（语义误导） |
| PoW / 图片验证码 | **fail-closed**：同样 **503**（与上一行统一） | 挑战是认证闸门，不能跳 |

⚠ R2：不要降级到"进程内存计数"——多 worker 下等于半 fail-open，且状态不可见。
⚠ 小站 Redis 抖动通常是秒级：503 比"全锁"或"放行"都诚实，且与下一行语义一致。

⚠ 实现时**不要一个 try/except 全放行**，按上表分开写。

### 5.6 两个已知的资源风险（不在本阶段解决，先记账）

```
① 导出 500 篇若**同步**生成 CSV/JSON ⇒ 内存峰值
   ⇒ 额度先降到 2 次/分钟；将来改异步（生成任务 + 限时下载链接）
② 验证码生成是 CPU 活 ⇒ 发图接口必须限速（见 9.5）
```

## 七、匿名按 IP 的误伤，三个缓解

```
① 登录用户**不占** IP 额度
   一个小区 50 人，登录 40 个 ⇒ 匿名额度只被剩下 10 人消耗

② 额度按"一家/一办公室"的量级定
   搜索 5 次/秒：正常人 1 秒点不到 2 次 ⇒ 一家三口共用也够

③ 超限先 429，反复超限才要 PoW
   真人最多多花 1 秒；脚本要付算力
```

## 八、PoW（工作量证明）设计

### 8.1 原理（★ 单位是**二进制位**，不是十六进制字符）

```
服务端给随机 challenge（十六进制串，32 字符）
客户端从 0 开始试 nonce（**十进制字符串**）
通过条件：  int.from_bytes(sha256((challenge + nonce).encode()).digest())
            <  2 ** (256 - N)
等价说法：  哈希值的**前 N 个二进制位**为 0
平均需要 2^N 次哈希（客户端）；验证只需 1 次（服务端）
```

⚠★ **"位"必须写死**：若实现成"前 N 个十六进制字符为 0"，实际难度是 4N 位
（N=18 ⇒ 2^72），桌面算到宇宙尽头也算不出来。

### 8.2 难度与耗时（N 为**位**）

| 难度 N（位） | 平均哈希次数 | 桌面 (~200 万/秒) | 中端手机 (~50 万/秒) |
|---|---|---|---|
| 16 | 6.5 万 | 0.03 秒 | 0.13 秒 |
| 18 | 26 万 | 0.13 秒 | 0.5 秒 |
| 20 | 105 万 | 0.5 秒 | 2 秒 |
| 22 | 420 万 | 2 秒 | 8 秒 ⚠ 太慢 |

**默认 18；上限 22；前端算超过 3 秒则请求降难度重发。**

⚠ 计算必须放 **Web Worker**（N=22 时主线程会卡死，页面假死比慢更糟）。

⚠★ **"降难度重发"的语义**：对**同一个未消费的 challenge** 把 Redis 里的
   `difficulty` 下调一次（⛔ 不发新 challenge、旧的不作废）⇒ 客户端不必重新取题。
   该接口要限速（每 token 每分钟 1 次），且只允许降一次（防"反复索取低难度"）。

### 8.3 流程与校验

```
① POST /api/challenge        服务端生成 challenge，存 Redis：
                             cap:pow:<challenge> = {action, difficulty}, TTL 300
② 前端（Web Worker）暴力试 nonce
③ 提交时带上 {challenge, nonce}
④ 服务端校验：存在？未用过？动作匹配？哈希 < 2^(256-N)？
   ⚠★ **N 必须从 Redis 的 challenge 记录里读**，⛔ 绝不信任客户端传来的 difficulty
      （否则攻击者传 difficulty=0 就直接通过）
   ✓ 通过 ⇒ **先删再执行**（GETDEL，防重放）⇒ 执行操作
```

⚠ **不比对** challenge 里是否同一个 ip：PoW 证明的是"付出了算力"，不是"同一个 IP"；
  手机在 WiFi / 4G 之间切换很常见，比对会让正常用户被拒。

### 8.4 必须做对的五件事

```
① 题存服务端，不把答案编码进题里
② 一次性：验证前就删（原子 GETDEL）
③ 绑动作：登录的题不能拿去换搜索
④ 发题接口自己限速（否则有人刷你的 Redis/CPU）
⑤ nonce 的字符串格式约定死（十进制），否则前后端算出的哈希不一致
```

### 8.5 局限（坦白）

```
✅ 挡得住：requests / curl 直接打接口的脚本
🔸 有限：会跑 JS 的爬虫（Playwright）—— 它们能算，只是变慢
❌ 挡不住：有 GPU 农场 / 代理池的定向攻击
⇒ PoW 的定位是"抬高低成本滥用的门槛"，不是防定向攻击
```

## 九、图片验证码（最终兜底 · 2026-11-04 所有者确认要做）

> 所有者原话：「验证码那个图片也做，作为最后的兜底，这个除了 OCR 扫描，一般还是难以攻破的。」

### 9.1 它在整条链里的位置

```
第 0 层  429 + Retry-After           （当秒恢复，真人无感）
第 1 层  蜜罐字段 + 时间陷阱           （挡不动脑子的机器人）
第 2 层  PoW 工作量证明               （挡"会写脚本但不愿花钱"）
第 3 层  **图片验证码**  ← 本节       （挡"连算力都愿意花"的）
第 4 层  短封（5 分钟起，自动过期）     （人工/自动，最后手段）
```

**定位：不是为了"防住所有机器人"，而是让每一次自动请求都变得更贵。**
OCR 打码平台约 1 美元/1000 次 —— 目标是让"刷这个站的性价比"低于"正常用"。

### 9.2 触发条件（什么时候弹图）

```
① 登录：同一 **IP** 失败 ≥ 20 次 / 15 分钟        ← ⚠ P4 之后才启用
② 匿名搜索：同一 IP 在 60 秒内被 429 达 10 次      ← ⚠ P4 之后才启用
③ PoW 通过后仍在 60 秒内超限（说明是"会算的脚本"）  ← ⚠ P4 之后才启用

⛔ **用户名维度不弹图** —— 那是**硬锁**（429 + Retry-After: 900，见 5.3）：
   同一个用户名第 6 次不可能既"被锁"又"过图"，两者语义不能混（N2）。
   ⛔ **不做过图解锁**（2026-11-04 已定）：锁定就是硬等到期；
      解除只有两条路 —— **管理员脚本**（`unlock-login.sh`）或**等 TTL 自然到期**。
      （详见 10.7；过图解锁会削弱锁定强度，明确不做）
```

正常用户永远看不到它：上述条件对真人来说都不可达。

⚠★ **登录路径的挑战其实很少触发**（S3）：密码登录只服务少数朋友
   （其他人走 OAuth，见 10.6.1）⇒ 本方案挑战机制的主战场是**匿名搜索**，
   不是登录。别把登录当成重点去优化。

⚠ Lua 返回 `missing`（token 不存在/已用/过期）⇒ 一律 **400**，并提示"请换一张"。

### 9.3 生成（服务端，Pillow）

```
字符集   4 位，去掉易混字符：不含 0O1lI、不含大小写同形
绘制     随机字体尺寸/位置 + 2~3 条干扰线 + 噪点 + 轻微旋转（-15°~+15°）
背景     浅色随机渐变（不要纯白，纯白更容易 OCR 预处理）
返回     image/png
        ⚠ 响应头必须带 Cache-Control: no-store（否则被中间层缓存 ⇒ 一张图反复用）
```

⚠★ **字体必须在镜像里显式安装**：容器里不一定有 DejaVu。
   ⇒ Dockerfile 加 `fonts-dejavu-core`（或 COPY 一个 ttf 进镜像）
   ⇒ 找不到字体时**启动即报错**（在 `AppConfig.ready` 或 settings 加载时检查文件存在），
     ⛔ 不要静默退回默认字体，也⛔不要拖到"首次生成"才暴露（那时第一个用户才踩雷）

### 9.4 传递与校验（★ 答案与 token 都不能泄露）

```
获取：GET /api/captcha/new
     返回 JSON：{"token": "...", "image_base64": "iVBORw0..."}
     ⛔ 不要设计成 GET /captcha/img/<token> —— token 会进访问日志 / Referer
     （与本节自己的禁令冲突，B8）

生成：token = secrets.token_urlsafe(16)
     Redis（**一个 hash 装全部**，TTL 一起走 —— 不留孤儿 key）：
       HSET  cap:img:<token> answer a7k2 action login tries 0
       EXPIRE cap:img:<token> 300

校验：**不是一次性**，而是"最多 3 次"（A3）—— ⚠ 用**一段 Lua** 保证原子

  local n = redis.call('HINCRBY', KEYS[1], 'tries', 1)
  if n == 1 then redis.call('EXPIRE', KEYS[1], 300) end     -- ★ 新建即补 TTL
  local ans = redis.call('HGET', KEYS[1], 'answer')
  local act = redis.call('HGET', KEYS[1], 'action')
  if not ans then return {'missing', '', n} end
  if ans == ARGV[1] and act == ARGV[2] then
      redis.call('DEL', KEYS[1]); return {'ok', ans, n}
  end
  if n >= 3 then redis.call('DEL', KEYS[1]) end             -- 第 3 次失败作废
  return {'bad', ans, n}

  参数：KEYS[1]=cap:img:<token> · ARGV[1]=用户输入(normalize 后) · ARGV[2]=本次动作

  ⚠★ **不能拆成 EXISTS → HINCRBY**（R1）：两步之间 key 可能正好过期，
     那时 HINCRBY 会**新建一个没有 TTL 的 key**，永久残留。
     ⇒ "残留由 TTL 兜底"这句话是**错的**，只有"新建时就补 EXPIRE"才成立。
  ⚠★ 校验与删除必须在**同一段 Lua** 里（S1）：否则两个并发请求带同一正确答案
     会各自通过一次（"比对 → DEL"之间是窗口）。Lua 天然串行，这个问题消失。
  ⚠ 不比对 ip（NAT / 移动网络会变）
```

**为什么选"3 次"而不是一次性**：4 位去混淆字符集约 80 万组合，
3 次暴力概率可忽略；而"输错一次就换图"对真人体验很差（尤其手机）。

### 9.5 防滥用（图片本身也是资源）

```
· 发图接口自己限速：每 IP 每分钟最多 5 张（否则有人刷图打 CPU）
· 每个 token 最多校验 3 次，第 3 次失败即作废（见 9.4）
· 失败计入审计（kind=rate_limited 或专门一类），便于以后看攻击形态
· 图片尺寸固定小（120×40），单张 CPU 约 1~3 ms
```

### 9.6 无障碍（★ 备选不能泄露图中字符）

```
✅ 「看不清？换一张」—— 重新发图，旧 token 作废
✅ 备选是**另一道题**：算术题（"3 + 5 = ?"），与图片共用 token/校验流程，
   但答案**不同源**（⛔ 绝不能把图中那 4 个字符用文字渲染出来 —— 那等于把答案交给机器人）
❌ 不做语音验证码（成本高、收益低，本阶段不做）
```

### 9.7 依赖与代价（要如实记账）

```
+ Pillow（约 3 MB，PIL fork，HPND 许可）
  ⇒ 进 requirements.txt ⇒ 每日 pip-audit 会一起扫
+ 字体：fonts-dejavu-core（或随镜像 COPY 一个 ttf）
- 不做：不引入任何第三方验证服务（Turnstile / reCAPTCHA / 打码平台）
```

### 9.8 局限（坦白）

```
✅ 挡得住：只要"能发请求"的脚本（它们不会去接 OCR）
🔸 有限：接打码平台的（约 1 美元/1000 次，延迟 1~3 秒/次）
❌ 挡不住：愿意为"单次请求"付 1 分钱且有耐心的定向攻击
⇒ 所以它排在第 3 层，后面还有"短封"兜底
```

### 9.9 验收标准

```
· 未通过验证码时提交 ⇒ 400（不是 500，也不是"静默失败"）
· 同一 token 第 4 次提交 ⇒ 400（前 3 次内正确仍可通过）
· token 过期（>5 分钟）⇒ 400
· 「换一张」后旧 token 失效
· 发图接口每分钟第 6 次 ⇒ 429
· 正常用户：一次输对 ⇒ 直接进入，不再弹图
· 镜像里没有字体 ⇒ **启动失败并明确报错**（不是等第一个用户触发验证码才发现）
```

## 十、登录失败计数（当前最大缺口）

### 10.1 现状

```
只有一条 access_audit.record("login_fail", ip, username)
⇒ 没有任何拦截：密码登录可以被无限撞
```

### 10.2 设计

```
计数键（Redis，TTL 15 分钟）
  rl:login:user:<规范化用户名>     ← strip().lower()
  rl:login:ip:<ip>                ← ⚠ P4 之后才启用（现在 IP 是网关）

判定（**必须在 authenticate() 之前**）
  用户名键 ≥ 5  ⇒ 直接拒绝，返回 429 + Retry-After: 900
                    ⛔ 不做密码哈希（否则锁定形同虚设，且 CPU 被放大）
  IP 键 ≥ 20     ⇒ 该 IP 的登录要 PoW（P4 之后）
```

### 10.3 三条必须守住的细节

```
① **检查位置在 authenticate() 之前**
   若先 authenticate()（触发 PBKDF2 ~100ms）再判锁定：
   攻击者对已锁用户名继续请求，每次仍付一次哈希 ⇒ 锁定无效 + CPU 放大
   （维护模式已经踩过这个坑，见 0.4）

② **用户名要规范化**：strip().lower() —— ⚠ **仅用于计数键**
   否则 Admin / ADMIN / admin 是三个键，计数可被轻松绕过
   ⛔ 但 `authenticate()` 仍用**用户原始输入**：数据库里的用户名可能大小写敏感，
      顺手 lower 掉会让合法用户登不进来（N7）

③ **不存在的用户名同等待遇**：同样计数、同样锁定、同样文案
   否则"被锁了 vs 密码错误"= 免费的用户名枚举 Oracle
   ⚠ 锁定文案必须与"密码错误"不可区分
```

### 10.4 清零与衰减

```
用户名键   登录成功 ⇒ **立即清零**
IP 键      **不清零**（只靠 15 分钟 TTL 自然衰减）
           ⚠ 若成功也清 IP 键：攻击者用 1 个合法账号"错 19 次 + 成功 1 次"
             ⇒ IP 防线被永久洗白
```

### 10.5 为什么 P1 只做"用户名"维度（A1）

```
现在 client_ip() 取到的是**网关地址**
⇒ 若 P1 就按 IP 计数，rl:login:ip:<网关> 是**全站共享**：
   任何人累计错 20 次，全站所有人的登录都要 PoW（严重误伤）
⇒ 拆成 P1a（用户名维度，真不依赖 IP）与 P1b（IP 维度，P4 之后）
```

### 10.5.1 「换用户名爆破」——★ 已决定接受（2026-11-04）

> 所有者原话：「换用户名爆破是可以接受的，写进方案里，就连大公司都不一定能扛得住
> 这种攻击方法，何况是我呢？我还有兜底开关。」

```
攻击形态  每个用户名只试 5 次（第 6 次锁），但换一个用户名继续试
P1b 之前  IP 维度尚未启用 ⇒ 应用层**没有**跨用户名的总闸
```

**为什么接受**：

```
① 这个攻击本质上无法用应用层彻底挡住
   账号密码验证天然是"每个名字可试 N 次"；跨名字的总量限制只能靠 IP/设备/风控，
   而前两者在真实 IP 就位前都不可靠（IP 塌成网关），风控模型对小站是过度设计
② 代价是双向的，但**我们这边确实要付 CPU**（⚠ 上一版这句写反了，已改正）
   每次失败都要跑一次 PBKDF2（约 100ms）—— 这是**服务端**开销，不是攻击者的
   攻击者付出带宽 + 请求生成成本；要打满一个 worker 需维持约 10 次/秒
   ⇒ 相比 GET 洪泛（几乎不耗 CPU），这种攻击"单位收益成本"更高，
     但**绝不等于"我们没成本"**：小站 worker 有限，被打时 CPU 会紧张
   ⇒ 这正是"保命开关"存在的理由，而不是"没有代价"
③ 本站账号总量极少（个位数）+ 注册需要邀请码
   ⇒ 可爆的"有效用户名"本来就少
```

**兜底：保命开关（不是"再写一层限流"）**

```
打开「站点保护模式」（后台按钮 / maintenance.sh on）后：
  · 登录入口只对 **staff 用户名**放行（其它一律 503，且不做密码哈希）
  ⇒ 换用户名爆破**当场失效** —— 攻击者连"试一次密码"的机会都没有
  · 只剩 admin 一个名字可试，而 admin 受"用户名 5 次锁定"保护
⇒ 也就是说：这个风险不是"放任"，而是"有一个 3 秒可用的开关能立刻掐死它"
```

⚠ 明确不做：`全站登录失败 > N/分钟 ⇒ 全体要 PoW` 这类兜底
   —— 它会误伤所有正常用户，而收益只是"把爆破速度降一点"；
      真被打了，**开保护模式**比这干净得多。

### 10.6 接受的风险

```
· 知道用户名即可把别人锁 15 分钟
· 不存在用户同样锁 ⇒ 不产生枚举信号
```

### 10.6.1 ★ 为什么"误锁"可以接受（所有者原话）

> 「用户名被锁后，只能硬等到时间到，除非我（管理员）手动给他打开……
>   我说了，密码登陆只是我的几个朋友可以，其他人都是 oauth 认证登陆，
>   我朋友密码被锁了，能找到我，他们也宽容许多。」

```
① **密码登录只服务极少数人**（几个朋友）
   其他人一律 GitHub / Gitee OAuth ⇒ 他们**根本不走密码这条路**，谈不上被锁
② 被锁的人**能找到你**（现实中的朋友），你能用脚本立刻解锁
   ⇒ 误锁的实际代价 = "发个消息 + 你跑一条命令"，不是"用户流失"
③ 因此：锁定的**收益**（脚本完全打不动）远大于**代价**（极少数人偶发等待）
```

⚠ 反过来看：如果为了"防误锁"放宽成"弹图解锁"，等于是为了极少数人
  把锁定的强度降一档 —— 那才是本末倒置。

### 10.7 解锁手段（★ 必须实现，否则 admin 会被锁死）

```
deploy/unlock-login.sh <username>      # SSH 执行，清该用户名的失败计数
deploy/unlock-login.sh --all           # 清所有用户名计数（极端情况）
deploy/unlock-login.sh --list          # 看谁被锁了、还剩多久
```

```
⚠ admin 账号**同样会被锁**（这是有意的：不因为"是管理员"就给它开洞）
  ⇒ 攻击者反复锁 admin 时：你 SSH 上去 `unlock-login.sh admin` 即可
  ⇒ ⛔ 不要给 admin 开"免锁定"白名单 —— 那等于把最值钱的账号暴露给无限爆破
```

⚠ 脚本要做的只有：
  · `DEL rl:login:user:<规范化用户名>`（以及 IP 键，如果已启用）
  · **写一条审计** `kind=login_unlock`（谁、何时、解了哪个用户名）—— 管理员操作必须留痕
  · 不需要重启、不影响其他会话

⚠ `--list` 用 **SCAN**（⛔ 不用 KEYS），单次最多列 100 条；小站够用。

## 十二、实施前置条件（★ 现在绝对不能做）

```
1  隧道**覆盖**写 X-Forwarded-For（⛔ 不能追加客户端带来的值）
2  nginx 打开 realip：
     set_real_ip_from <隧道所在网段或 127.0.0.1>
     real_ip_recursive on
   ⛔ 现在打开 = 客户端自带的 XFF 会被当成真实 IP（比不开更糟）
3  proxy_set_header X-Forwarded-For 从"追加"改为 `$remote_addr`（覆盖）
4  80 端口从 0.0.0.0 改为 127.0.0.1（外网只能经隧道进）
5  ★ 完成 1~4 之后，client_ip 才可信 ⇒ M1/M3/nginx 限流才有意义
```

⚠ 顺带要重定 `is_bannable()` 的白名单：隧道如果在容器内，它的地址会是内网段。

## 十三、实施计划（分阶段，可回滚）

| 阶段 | 内容 | 依赖 | 预计 |
|---|---|---|---|
| **P0** | 文档 + 两轮审查修订 | — | 已完成 |
| **P1a** | 登录失败计数（**用户名硬锁 429** + `unlock-login.sh` 解锁脚本） | 无 | 半天 |
| **P1b-1** | 登录失败计数（**IP 维度**，超限先**硬拒 429**，不做挑战） | **P4** | 半天 |
| **P1b-2** | 把 IP 维度的 429 换成"要 PoW" | **P5** | 半天 |
| **P2a** | 写操作限流（发布 / 删除 / 导出） | 无 | 半天 |
| **P2b-1** | 读 / 搜索限流（**只收紧登录用户**的额度） | 无 | 半天 |
| **P2b-2** | 匿名按 `a<ip>` 分桶 + 收紧到 5 次/秒 + 注册限流 | **P4** | 半天 |
| **P3** | 删/降级设备令牌 | — | ✅ **已完成（2026-11-04）** |
| **P4** | 隧道就绪 → realip → nginx 限流（连接/速率）+ 封禁双写 | **等隧道** | 半天 + 联调 |
| **P5** | PoW（挑战 / 校验 / 难度自适应 / Web Worker） | P4 之后 | 1~2 天 |
| **P6** | 图片验证码（生成 / 校验 / 无障碍 / 字体） | P5 之后 | 1 天 |
| **P7** | 封禁改造（短封 + 倒计时 + nginx 侧拦截） | P4 之后 | 半天 |

⚠★ **为什么 P1b / P2b-2 / 注册限流都压在 P4 之后**（N1/N3/N5）：
   它们都按 IP 计账，而 P4 之前"IP"就是网关 ⇒ 会退化成**全站共享**，
   上线即误伤。P1a / P2a / P2b-1 只按用户名计账，与 IP 无关，所以现在就能做。

### 验收标准（每阶段）

```
P1a  同一用户名连错 5 次 ⇒ 第 6 次 429 + Retry-After: 900
     · **不做哈希**的验证方式：命中锁定时响应耗时 < 20ms，且
       在 authenticate() 前打点的日志里能看到"已锁定"且没有后续哈希记录
       （也可临时给 authenticate 加计数，锁定期内计数不增长）
     · 输对一次 ⇒ 用户名键清零；换大小写（Admin/adMIN）仍算同一个键
     · 不存在的用户名同样被锁，且**文案与密码错误不可区分**
     · `unlock-login.sh <name>` 立刻解锁（下一个请求即可正常登录）
     · `unlock-login.sh admin` 能解开 admin 自己的锁
P1b-1（P4 后）同一 IP 20 次失败 ⇒ 该 IP 的登录 429；其他 IP 不受影响
P1b-2（P5 后）同上，但 429 改为"要求 PoW"；过了 PoW 才校验密码
P2a  连发 40 次发布 ⇒ 第 31 次 429；导出第 3 次 429
P2b-1 登录用户：搜索第 11 次/秒 ⇒ 429
     ⚠ 本阶段**匿名行为必须保持不变**：匿名普通读**不新增限流**；
        匿名搜索**维持 M2 现状（全站共享 10 次/秒）**，等 P2b-2 再改分桶
        （⛔ 不要顺手把 5.1 的匿名额度提前上了 —— 那就是 N1 的坑）
P2b-2（P4 后）匿名同一 IP 第 6 次/秒 ⇒ 429，且不影响其他 IP；
     注册第 4 次/小时/IP ⇒ 429（P4 前该条不生效）
P3   ✅ 已完成：无 at_device Cookie；/admin/access/ 5 个 tab；冒烟全过
P4   伪造 XFF 不生效；nginx 日志出现真实 IP；
     单 IP 并发 40 ⇒ 第 31 个连接 **429**（⚠ 需配 limit_conn_status 429）；
     被封 IP 在 nginx 层即被拒（不进入 Django）
P5   需要 PoW 的请求不带 nonce ⇒ 400；普通请求不带 nonce 照常 200；
     同一 nonce 二次使用 ⇒ 400；难度按历史自适应
P6   未过图 ⇒ 400；同 token 第 4 次 ⇒ 400；过期 ⇒ 400；换图后旧 token 失效；
     发图第 6 次/分钟 ⇒ 429；**无字体 ⇒ 启动失败**
P7   封 5 分钟 ⇒ 5 分钟后自动解；后台显示剩余时间；nginx 与 Django 双写一致
```

### 依赖关系（一图看清）

```
现在就能做（只按用户名/账号计账，与真实 IP 无关）
  P1a（含 unlock-login.sh）· P2a · P2b-1

等隧道（P4）之后
  P4 ──┬── P1b-1（IP 维度 429）
       ├── P2b-2（匿名分桶 + 注册限流）
       └── P7（封禁双写）
  P5（PoW，需 P4）──┬── P1b-2（429 → PoW）
                    └── P6（验证码）
```
