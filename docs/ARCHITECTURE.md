# 架构分层与边界

> **本文的地位**：⚠ **分层边界以本文为准**。与 `backend-modular-architecture.md` 等旧文档冲突时，**以本文为准**。
> **为什么先写它**：旧项目"功能越堆越脏"的根因不是代码质量，而是**没有一条「谁不许变成谁」的纪律**。
> **写作时间**：2026-09-18（开工之前，尚无代码）

---

## A0 三条原则（先立规矩）

| # | 原则 | 判据 |
|---|---|---|
| **1** | ★ **数据性质决定并发模型** | 图 = **复制型权威数据** ⇒ 冲突是**静默分叉**（无人察觉）⇒ **单写者 + 串行**；UGC = **条目级多写者** ⇒ 条目级 `rev` CAS 即可 |
| **2** | ★ **重活不上 Web 线程** | 任何**耗时 ≥ 1 秒**的操作**一律走队列**。⚠ 违反 = 单机凭空丢掉大部分容量 |
| **3** | ★ **Web 层无状态** | Django 进程内**不保存**任何跨请求状态（session / 缓存 / 临时文件 → Redis / 对象存储）。⇒ 将来扩容 = **加机器**，不是改代码 |

## A1 三层结构

| 层 | 技术 | 一句话职责 |
|---|---|---|
| **① Web / 业务** | Django（沿用） | 处理**请求**：API、权限、UGC 读写、管理后台、数据迁移 |
| **② 作业 / 解析** | Python worker（沿用 systemd 模式） | 处理**耗时任务**：拉源码、排队、解析、产图 |
| **③ 计算** ★ | 独立服务（**语言自由**：先 Python，将来可 Go / Rust） | 处理**重计算**：图算法、全图遍历、加速器池 |

⚠ ③ **一期可以不做**，但 ★ **边界现在就必须留出来**。

---

## A2 每层「做什么 / 明确不做什么」

| 层 | 做 | ★ 明确不做 |
|---|---|---|
| **① Web** | 校验请求、读写 PG、**写 Job 记录**、返回 JSON | ❌ 解析代码　❌ 拉远程仓库　❌ 全图遍历　❌ 存跨请求状态 |
| **② 作业** | 消费 Job、拉源码、调解析器、写图、更新进度 | ❌ 直接对外提供 HTTP　❌ 依赖 Web 的视图层代码 |
| **③ 计算** | 纯函数式图计算：吃图数据、吐结果 | ❌ 不连 PG（数据由 ② 喂）　❌ **不 import Django** |

---

## A3 ★ 依赖纪律（本文件的核心）

**允许的 import 方向**：

| 谁 | 可以 import |
|---|---|
| **共享内核**（模型 / schema / 常量） | 只依赖标准库与 ORM |
| **① Web** | 自己的模块 + 共享内核 |
| **② 作业** | 共享内核 + 解析器 |
| **③ 计算** | ★ **只依赖标准库 / 第三方计算库** |

**❌ 禁止（红线）**：

1. ❌ **② 作业层** import **① 的视图 / 序列化器 / URL 配置**
2. ❌ **① Web 层** import **② 的执行代码**（`run_worker` / `jobs.tasks`）
   ★ **精确化（`B131`）**：⚠ 红线 #2 的**本意是「不得在 Web 请求里【执行】耗时工作」**
   （那会让 web 线程被占住 ⇒ 单机凭空丢掉大部分容量）。
   ★ 但**字面**执行会得出一个荒谬结论：① 不能把作业推进队列
   ⇒ ① 就只能"写 Job 记录然后等别人来捞"，必须额外引入**轮询 Job 表**的第二套机制。
   ★ **口径**：✅ ① 可以 import **`jobs/dispatch.py`（投递）**；
   ❌ ① 不得 import **`run_worker` / `jobs.tasks`（执行）**。
   ⚠ 判据：**「投递」是 O(毫秒) 的两次写，「执行」是 O(分钟) 的重活。**
3. ❌ **③ 计算层** import **Django / ORM / 任何 ① ② 的模块**
4. ❌ 任何层绕过共享内核、**自己定义数据模型**

> ★ **判断法则**：**能互相 import 的东西，迟早会长成一坨。**
> 跨层一律走 **队列 / API / 数据**，不走函数调用。

## A4 跨层通信契约

| 方向 | 方式 |
|---|---|
| **① → ②** | **写 Job 表**（`kind` + `dedup_key` + payload）—— ⚠ **不是函数调用** |
| **② → ①** | **更新 Job 状态 / 写结果表**，Web 层**轮询**读进度 |
| **② ↔ ③** | 一期：进程内函数调用（⚠ 但**接口按"将来要拆出去"来设计**）；将来：RPC |
| **③ → 外界** | 只吐**数据**，不直接写库 |

## A5 技术选型与并发结论

**保留 Django**，四条理由：

1. ★ **重活不经过 Web 层** ⇒ Django 只扛"十几毫秒的读 + 几毫秒的写"
2. ✅ ORM + migration + admin 是**图数据建模**的最强项
3. ✅ 现有 auth / 部署 / 前端契约**可直接复用**
4. ⚠ **瓶颈通常不在 Django，在 PostgreSQL** —— 只要邻域查询**有索引**即可

**容量参考（单机）**：

| 日活 | 峰值并发 | 单机 Django + PG |
|---|---|---|
| 1,000 | ~50 | ✅ 够 |
| 10,000 | ~300 | ✅ 够（+ ASGI + Redis 热点缓存） |
| 100,000 | ~3,000 | ⚠ 多机 + 只读副本（★ 那时已经成功了） |

## A6 扩展开关（**有触发才动，不提前做**）

| 触发信号 | 动作 | 改动范围 |
|---|---|---|
| p95 延迟 > 500ms | 加 **Redis 缓存热点图** | ① |
| PG CPU 持续 > 70% | 加 **只读副本** | ① |
| 单机 CPU 打满 | ★ **加第二台 Web + 负载均衡**（因 A0-3 已满足 ⇒ **加机器即可**） | 部署 |
| 全图算法变慢 | **③ 换语言**（Go / Rust） | ③ |

---

## A7 现在就做的 5 件事（几乎零成本）

1. **静态资源交给 nginx / CDN** —— 砍掉 80%+ 流量
2. **Web 层无状态**（A0-3）
3. **图查询必带索引**
4. **重活一律走队列**（A0-2）
5. 部署用 **ASGI 就绪**的配置（随时可切）
