## J1 ★ 三层并发模型（**核心认知**）

| 层 | 并发能力 | 受什么限制 | 说明 |
|---|---|---|---|
| **① 投递** | ★ **极高**（数千并发无压力） | 几乎无限 | 只写一条 Job + 推队列，**毫秒级** |
| **② 排队** | ★ **无限** | 无 | 不消耗资源，只是"在等" |
| **③ 执行** | ★ **3–4 个并行** | ⚠ **核数 + 内存** | 解析是 CPU 密集型 |

> ★★ **结论**：**用户感受到的"并发"，99% 来自 ① 和 ②** —— 而这两层**没有上限**。
> 唯一的硬约束是 ③，而它**只需要"够快"，不需要"无限"**。

## J3 Job 表结构（草案）

```sql
CREATE TABLE job (
  id             bigserial     PRIMARY KEY,
  project_ref    char(32)      NOT NULL,
  kind           varchar(32)   NOT NULL,   -- parse / index / ...
  state          varchar(16)   NOT NULL,   -- queued / running / done / failed / canceled
  payload        jsonb,                    -- 参数（如 repo / commit / 语言范围）

  dedup_key      varchar(128),             -- ★ 幂等键：相同 ⇒ 合并，不新建
  priority       smallint      NOT NULL DEFAULT 0,  -- ★ 数值越大越优先（小项目优先）

  queued_at      timestamptz   NOT NULL DEFAULT now(),
  started_at     timestamptz,
  finished_at    timestamptz,

  progress       smallint      NOT NULL DEFAULT 0,  -- 0–100
  stage          varchar(64),              -- ★ 人类可读阶段（"正在解析 src/main.c"）
  eta_s          integer,                  -- ★ 预计剩余秒数

  attempts       smallint      NOT NULL DEFAULT 0,
  error_code     varchar(64),
  error_msg      text,
  worker_id      varchar(64)
);

-- ★ 队列取作业：按 (priority DESC, queued_at ASC)
CREATE INDEX ON job (state, priority DESC, queued_at ASC);

-- ★ 每用户并发与排队查询
CREATE INDEX ON job (project_ref, state);
```

> ★ **`queue_position` 不落库** —— 由「`state='queued'` 且排在前面的人数」**动态计算**（避免高频写）。

## J4 状态机

```
           ┌─────────────┐
           │   queued    │ ← 投递即入此状态（★ 永不拒绝）
           └──────┬──────┘
                  │ worker 领取
           ┌──────▼──────┐
           │   running   │──→ 定期回写 progress / stage / eta_s
           └──┬───────┬──┘
              │       │
     成功 ┌────▼──┐    │ 失败
          │ done  │  ┌─▼────────┐
          └───────┘  │  failed  │──→ attempts < N ? 重回 queued : 终态
                     └──────────┘
   任意状态（queued/running）──→ canceled（用户取消 / 超时）
```

★ **状态只有 5 个**：`queued / running / done / failed / canceled` —— ❌ 不再引入旧设计里的额外状态。

## J5 ★ 并发与排队策略（**本节是重点**）

| 项 | 规定 | 理由 |
|---|---|---|
| **投递** | ★ **永不拒绝**（除非超过**硬配额**，且必须给出**明确提示**而非静默） | ⚠ 旧设计「投递被拒 → 项目直接 error」是最大体验杀手 |
| **排队** | ★ **不限数量**（每用户可同时排队任意个） | 排队不消耗资源 |
| **执行** | ★ **每用户同时 1 个**（防独占）；**全局并行 = `min(核数-1, 内存允许)`** | ★ 按**实测核数与内存**推导（⚠ 具体值已脱敏） |
| **幂等** | ★ `dedup_key` 相同 ⇒ **合并到已有 Job**（返回同一个 `job_id`），**不是新建、更不是报错** | ⚠ 旧 `B14` 的「静默拒绝」正是"卡"的来源之一 |
| **优先级** | ★ 数值越大越先跑；**小项目给高优先级**（快速周转，用户体感最好） | 大项目离线慢慢跑 |
| **进度** | ★ **必须回写** `progress` / `stage` / `eta_s` | 排队可见性 |
| **超时** | 单作业硬超时（可配），超时 → `failed` + 明确原因 | 防僵尸作业 |

> ⚠ **反面清单（禁止）**：
> ❌ 投递被拒时静默丢弃　❌ 用「每用户全局 1」限制**排队**　❌ 只在失败时给用户一个 `error` 状态

## J7 ⚠ `B115` 四条硬要求 → **验收判据**

| # | 要求 | 怎么算通过 |
|---|---|---|
| **1** | ★ **投递即入队** | 投递任何项目**都返回 `job_id`**（除非超硬配额，且返回**明确错误码**） |
| **2** | ★ **排队状态可见** | 接口能返回 `queue_position` / `eta_s` / `stage`；前端能显示"第 N 位，约 M 分钟" |
| **3** | ★ **并发粒度合理** | ❌ 不存在「每用户全局 1」这种把**排队也**限死的规则 |
| **4** | ★ **幂等键语义正确** | 同一 `dedup_key` 重复投递 ⇒ **返回同一个 `job_id`**，**不报错、不静默丢** |

> ⚠ **旧缺陷对照**（`B115` 记录的线索，实现时逐条检查是否重犯）：
> · `B14`：`dedup_key = dedup_key(KIND_PARSE, "proj:<ref>")` ⇒ 同项目重复投递**被静默拒绝**
> · `B7`：硬失败语义 ⇒ 用户侧表现为**项目直接置 `error`**
> · `job_max_per_user = 1` ⇒ **全局串行**
> · 主文 §8.1：投递被拒 → 项目直接 `error`

## J9 架构归属（与 `ARCHITECTURE.md` 对齐）

```
① Web（Django）  ── 写一条 Job + 推 Redis 队列 ──→ 立刻返回 job_id
        ↑                                              │
        │ 轮询读 job 表（position / stage / eta）        │ ★ 不是函数调用
        │                                              ▼
② 作业层（独立进程池）  ←── 从队列领取 ──→ 执行解析 → 写回 job 表 / 结果表
        │
        ▼（全图算法）
③ 计算层（独立，可换语言）
```

★ **纪律**：① **不得 import** ② 的 worker 代码（`ARCHITECTURE.md` A3 红线）—— 只通过 **Job 表 + 队列**通信。
★ **队列中介用 Redis**（不占 PG 连接），与 `S2.2` 的「Redis = 共享易失状态」定位一致。

### J10.2 ⚠ 汇编的特殊处理（用户提出「Linux 内核有大量汇编」）

**事实核查**（2026-09-19）：

| 语法包 | 情况 |
|---|---|
| `RubixDev/tree-sitter-asm` | ✅ 存在，但是 **Generic（通用）** 语法；⚠ 仅 28 stars，冷门 |
| `bearcove/tree-sitter-x86asm` | ✅ 存在（Intel x86）；⚠ 2022 年后基本不活跃 |
| `tree-sitter-language-pack` | ✅ 一个包覆盖 **371 种语言**（含 C / C++ / Python / Java） |

⇒ ★ **结论**：**汇编有包，但"通用语法"对 Linux 内核那种 x86 / ARM 汇编大概率不够。**

**一期建议（三选一，推荐 A）**：

| 方案 | 说明 |
|---|---|
| **A ★ 推荐（一期）** | ★ **不做指令级解析，只做"符号提取"** —— 用轻量词法提取 `ENTRY(x)` / `GLOBAL(x)` / `SYMBOL_NAME(x)` / `EXPORT_SYMBOL` 等，**作为节点暴露**；❌ **不建汇编内部的调用图** |
| **B 用 `tree-sitter-asm`** | ⚠ 通用语法，覆盖不全；**可作为符号提取的补充** |
| **C 自写完整汇编语法** | ⚠ 工作量大、收益低 —— **留作后手** |

> ★ **理由**：读内核的人真正关心的是「**入口点在哪**」「**汇编与 C 的边界在哪**」，
> 而不是汇编内部的跳转关系 —— 而后者大部分是**宏展开**的产物，价值低。

### J10.3 ★ 统一 Parser 接口与注册表（**将来要能无缝换成自写语法**）

**用户原话**：

> 主要是要**兼容**。以后，我写一个专门解析汇编语言的语法文件，要能**很方便地嵌进现在的网站源码里使用，不用修改太多** —— 我可以**按照 tree-sitter 的规则**写汇编语言解析器。

#### ① 统一接口

```
Parser.parse(source: bytes, path: str) -> ParseResult
       ★ ParseResult 是【统一中间结构】
```

#### ② ★ 实现注册表（**替换即改一行**）

```python
LANG_PARSERS = {
    "c":      TreeSitterParser("c"),
    "cpp":    TreeSitterParser("cpp"),
    "python": TreeSitterParser("python"),
    "java":   TreeSitterParser("java"),
    "asm":    AsmSymbolParser(),          # ★ 一期：轻量符号提取（J10.2 方案 A）
    # "asm":  TreeSitterParser("asm"),    # ★ 将来：自写语法 → 替换这一行即可
}
```

#### ③ ⚠ 硬约束（**成败关键**）

```
★ AsmSymbolParser 的产出【必须与 TreeSitterParser 结构完全一致】
   —— 否则将来自写语法【接不进来】，就得改下游代码
```

#### ④ 纪律

```
⚠ ParseResult 不得暴露 tree-sitter 的节点类型
   —— 否则下游会被绑死在 tree-sitter 上
```

★ 这与 `GRAPH-STORAGE.md` G6「**接口按语义定义，不按实现定义**」是同一条原则。
★ **验收方式**：一期的 `AsmSymbolParser` 与 `TreeSitterParser` 用**同一套下游消费代码**跑通 —— 能跑通，就证明替换可行。
