### G10 · ⚠ 纠正 · 2026-11-14 09:10 · 不许拿哈希 vid 当主键

> 「不行，不能拿vid当主键，这个vid不一定是唯一的，一旦节点数量变多，会哈希碰撞，
> 还有许多奇奇怪怪的原因，或者不小心输入了相同的值，那就会重复」

**我错在**：把 `hash53` 的「理论唯一」当成了工程保证，没有对现实中的脏数据、碰撞做准备。

**结论**：**必须依赖数据库的主键唯一约束**，不能靠应用层「算出来应该不撞」。
实测：`Found duplicated primary key value 1, which violates the uniqueness constraint`，
原数据完好、事务整体回滚、零残留。

**落实**：主键唯一性交给 Kùzu；应用层只负责「撞了之后怎么办」。
**状态**：已实施。

### G11 · ⚠ 纠正 · 2026-11-14 09:15 · 主键不需要用户操心

> 「不对哦，图数据库怕是不需要我设置主键吧？我现在需要用到主键吗？」

**我错在**：把主键当成一个需要反复权衡、请所有者拍板的设计项。

**实测结论**：`CREATE NODE TABLE` **不写 `PRIMARY KEY` 直接报语法错**
`Parser exception: Can not find primary key.` ⇒ 主键是 **Kùzu 的语法强制项**，不是业务设计项；
业务查询一次都没按主键走过，全是按 `vid` 属性过滤。
另外 `_id`（内部 offset）被系统锁住：`_id is reserved for system usage. External access is not allowed.`

**结论**：主键只是语法占位，用什么字段由代码定，**不需要所有者决策**。

**状态**：已实施（认知纠正）。

### G12 · 2026-11-14 09:25 · 撞了就重算，不许冒到界面

> 「那就不用了，只要能收到主键重复报错就行，收到错误，立即处理重算一个哈希，
> 不要高处什么白屏，崩溃之类的出来就行。让vid当主键也可以，保证了其的唯一性。」
> （「不要高处」原文如此）

**结论**：**`vid` 当主键**（`PRIMARY KEY(vid)`，去掉 `code:<vid>` 字符串包装）。
撞主键时在内部消化，绝不冒到界面：

| 撞上的是 | 处理 |
|---|---|
| 同 `kind/file/name/line` 的同一节点 | 重复添加 → 跳过 / 报「已存在」，⛔ 不造重复节点 |
| 不同内容（真哈希碰撞） | 加盐 `hash53(f"{canon}|{n}")` 再试，用户无感 |

**落实**：`graphdb._create_code` / `add_code`；批量快路径 + 撞主键回退逐条慢路径。
**状态**：已实施。

### G14 · 2026-11-14 08:48 · 删除后会不会复用 id

> 「这个图数据库会不会在删除一个节点后，新增节点时，复用已经被删除的节点id？」

**实测**：内部 offset 实测这次没复用（删 offset=1 后新节点拿 4），但 **Kùzu 不承诺回收策略**，
且 `_id` 外部不可访问 ⇒ 我们从不引用它，不受影响。
`vid` 按内容算：删掉 `foo` 再加 `bar` 绝不可能是同一个 id；删掉 `foo` 再加回同样的 `foo`，
id 相同 —— 那是**同一个节点**，不是复用。

**状态**：已实施（认知确认）。

### G16 · 2026-11-14 09:20 · 对哈希的现实担忧（最终定论）

> 「我只是担心这种通过哈希计算而出的高度不确定性的东西，做主键，会不会出现一些问题？
> 理论上是没有的，可现实不是理论，会有各种各样意想不到的情况，自增主键是最理想的，
> 这个图数据库设置的主键允许重复吗？插入了重复的主键会报什么错？」

**实测回答**：主键**不允许重复**，插入重复报
`Found duplicated primary key value ... violates the uniqueness constraint`，
原数据不动、事务回滚。
Kùzu **没有 `AUTO_INCREMENT` / `SERIAL`**，所谓自增只能应用层 `max+1` 维护，
并不能消除「`vid` 仍需唯一（它是笔记锚点）」这个事实，只是多一份计数器。

**结论**：**不自增**。保持 `vid` 主键 + 数据库唯一约束 + 撞了重算。
**状态**：已实施。

### G20 · ⚠ 纠正 · 2026-11-14 09:40 · 别自己造索引，要捕获数据库错误

> 「你这样一个循环查询，要输节点变多了，一个插入要多少时间，算过吗？
> 图数据库的主键约束好歹还是用二叉树来检测主键有没有撞上的，
> 我是要你捕获数据库发来的错误，撞了，就重算，有其他典型错误也处理一下。」
> （「要输节点」原文如此）

**我错在**：写了个「预读全表 `MATCH (c:Code) RETURN ...` → Python 建 `used` 字典 → while 查重」，
等于用手写哈希表替代数据库已有的 B+ 树；每次同步都白读一遍全表（1 万节点约 50–100ms 纯浪费）。

**结论**：**直接插，撞了再算**。
- 快路径：`UNWIND` 批量 + 单事务；
- 只在捕获 `duplicated primary key` 后回退逐条（自动提交，因为 Kùzu 语句失败会终止事务）；
- `_is_dup_pk()` 只认这一种错误，其它（缺主键、类型不符、事务异常）照常抛出；
- 回滚都套 `try`，避免 `No active transaction for ROLLBACK` 掩盖原错误。

**实测**：2000 节点 + 1999 边 713 ms；撞主键回退 113 ms（2 节点）；
模拟碰撞 `alpha` 保留原 vid，`Beta` 自动换 vid，零报错。

**落实**：`graphdb.py` 删预查段；新增 `_create_code` / `_is_dup_pk` / `_clear_code`。
**状态**：已实施。

### G21 · ⚠ 纠正 · 2026-11-14 09:45 · 单条插入才是日常路径

> 「你有没有考虑过除了一开始的解析是批量插入的，其他时候用户大多数是一条一条插入的」

**我错在**：只优化了「首次解析」的批量路径，改图面板的 `add_code` 还是「先 `_resolve_vid` 查一遍再插」的预查模式。

**结论**：三条写入入口统一「直接插 + 撞了再判断」：
`sync_code`（批量）、`add_code`（单条）、`_create_code`（共用底层）。
并且必须区分「同内容 = 重复添加，跳过」与「不同内容 = 哈希碰撞，加盐重试」，
否则重复添加会被当成碰撞而造出一个重复节点。

**实测**：单条插入平均 2.56 ms/条；重复添加被拒；模拟碰撞自动换 vid；同内容跳过且不增节点数。

**落实**：删 `_resolve_vid`；`add_code` 改为 `_create_code` 一行。
**状态**：已实施。

### G27 · 2026-11-13 17:40 · 节点能存多少信息

> 「这个图数据库里，一个节点可以存多少信息？」

**实测**（`ladybug` 0.22.3 / Python 3.12）：列数 ≥ 8000、单个 `STRING` ≥ 16MB、
支持 `BLOB` / `LIST` / `STRUCT` / `MAP`（MAP 须用 `map(["k"],["v"])`）；
**不支持 `ALTER TABLE ADD COLUMN`** ⇒ schema 必须一次性定好。

**结论**：能放正文，**但不该放** —— 图属性在遍历/返回时整块拷贝，
几百篇长笔记进图会拖慢所有图查询。由此引出 G5「正文不进图」。
**状态**：已实施。

### G28 · 2026-11-14 08:20 · 边和节点怎么没有主键

> 「·图数据库里边和节点怎么没有主键呢？这个图数据库不应该有一根自增的大整数做主键吗？」

**澄清**：节点**有**主键（`Code.id` / `Note.id` / `Board.id`），**缺主键的是关系表**。
Kùzu 把关系存成「按源节点的邻接表 + 内部偏移」，天然是多重集（`MANY_MANY`），
遍历按端点跳，不按边 id 查。

**实测**：`CREATE REL TABLE R2(FROM Code TO Code, eid INT64, kind STRING, MANY_MANY)` 可行、
`RETURN max(r.eid)` 可行、同端点同类型允许平行边；但**没有 `AUTO_INCREMENT` / `SERIAL`**，
`eid` 只能应用层 `max+1` 自己维护 —— 多一列、多一次聚合，换不来能力。

**结论**：不加边主键（引出 G8 / G15）。
**状态**：已实施。

### G29 · 2026-11-14 09:05 · 用数据库自动分配的 id 当主键（已否决）

> 「太麻烦了，既然语法要求必须要主键，那就用图数据库自动为节点分配的id当主键就完了呗，
> 只要主键不会重复就完了，这个ID虽然可能复用，但绝不会重复吧？」

**实测：Kùzu 不提供自动分配的 id。**

```
CREATE (:T {b:"x"})  → Binder exception: Create node expects primary key a as input.
RETURN z._id         → Binder exception: _id is reserved for system usage.
                        External access is not allowed.
```

插入时不给主键值直接报错；唯一的「自动 id」是内部 offset，被系统锁住、外部拿不到。

**结论**：这条路不存在。主键只能是我们自己提供的某个属性 —— 最终选 `vid`（G12）。
**状态**：**已否决（数据库不提供自动 id）**。

### G31 · 2026-11-14 11:16 · 代码节点之间不分方向只许一条边

> 「还有代码节点之间，无论方向，都最多只能有一条边。」

**结论**：**任意两个代码节点之间总共只有一条边**，方向只是这条边的属性，
不是区分两条边的依据。推翻 G8 里「反向可并存」的理解。

| 位置 | 改法 |
|---|---|
| `add_rel` | 双向查重：`(a,b)` 或 `(b,a)` 已存在即拒，提示「不分方向，只允许一条」 |
| `sync_code` | 按排序后的无向端点对 `(min,max)` 去重；**保留先到那条边原本的方向**，不把 `B→A` 改写为 `A→B` |
| `remove_rel` / `update_rel` | 按端点对定位，传反方向也能删/改 |
| 自环 | 仍禁止 |

**实测**：`A→B` 建立后再加 `B→A` 被拒；`A→C` 不受影响；
解析产物里同时给出 `B→A` 与 `A→B` 时只留 1 条且保留 `B→A`；
用反方向 `A→B` 删掉 `B→A`、改其类型均成功。

**落实**：`sidecar/graphdb.py`（`add_rel` / `sync_code` / `remove_rel` / `update_rel`）。
**状态**：已实施。
