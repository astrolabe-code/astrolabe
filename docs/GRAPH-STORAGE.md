#### ★ 接口（契约 `frontend-contract.md` §2 已定义，❌ 不另起一套）

```
POST /api/projects/<project_ref>/graph/edit/
body: {base_graph_rev?, reason, changes: [ {action, ...}, ... ]}
resp: {ok:true, data:{graph_rev, applied}}

GET  /api/projects/<project_ref>/graph/manual/     → 哪些是人补的（origin=manual）
```

★ 六种 `action`：`add_node` / `update_node` / `remove_node` / `add_edge` / `update_edge` / `remove_edge`

| 情况 | 状态码 |
|---|---|
| 未登录 | **401** `unauthenticated`（★ 明确信号，⚠ 不是越权） |
| ★★ 不是这个项目的人 | **404**（★ **与"不存在"同形**） |
| 坏 JSON / 没填理由 / 动作不认识 | **400** |

| ✅ 成功 | **200** `{graph_rev, applied}` |

#### ★★★ 批量：一次操作 = **一个事务 + 一条审计 + bump 一次**

| | 一条一发 | ★★ 一批 |
|---|---|---|
| 事务 | ⚠ N 个事务 ⇒ **改到一半失败 = 半个修补** | ✅ **要么全成、要么全不成** |
| 审计 | ⚠ N 条 ⇒ **看不出是一件事** | ✅ **一条**，看得出"他一次干了什么" |
| `graph_rev` | ⚠★ **跳 N 次** ⇒ 邻域缓存**反复失效** | ✅ **只 +1** |

⚠★★ **踩到的坑（很隐蔽，后果严重）**：

```python
with transaction.atomic():
    ...
    if not r.ok:
        return ...        # ❌ **会 COMMIT！** 前面几条真的写进去了
```

★ 因为 `atomic()` **只在【抛出异常】时回滚**，`return` 是**正常退出** ⇒ ★ **照样提交**。
★ 实测抓到：整批报失败，**第 1 条却生效了**。
⇒ ★★ 必须**抛**出去，且 `except` 写在 **`with` 外面**（⚠ 在里面接住 = 又变成正常退出 = 又提交）。

#### ⚠★ `reason` 必填 —— ★ 它的立法理由就是 `§2.3.12` 规则 4

> **「用户全权负责」的技术前提就是「可追溯」——**
> **没有审计，「全权负责」就变成「没人负责」。**

★ 所以这不是"流程规定"：★ 网页上维护者**必须填一句理由**，
★★ 而那句理由是**给半年后的他自己**看的（⚠ 删掉的东西在别处再也查不到了）。
| **影响** | ★ 修补**概率小、不频繁** ⇒ **缓存策略依然成立**（见 G5） |
| **配套** | 勘误建议复用 UGC 通道；★ **删节点不删解释**（`§2.3.12`） |

## G2 ★ 分层策略（深度决定手段）

| 跳数 | 手段 | 预期耗时 | 说明 |
|---|---|---|---|
| **1 跳** | 邻接表 + **索引扫描** | ★ **< 1 ms** | 一次索引查找 |
| **2 跳** | **递归 CTE**（2 次索引扫描） | ★ **2–5 ms** | ⚠ **不必预计算** |
| **3–4 跳** | 递归 CTE + **深度硬上限 + 结果上限** | 几十 ms | ⚠ 必须截断 |
| **全图算法**（环 / 聚类 / 影响面 / 最短路径） | ★ **③ 计算层，异步** | 秒级 | ⚠ **不上 Web 线程**（`ARCHITECTURE.md` A0-2） |

> ★ **结论**：**「点击节点看关系」用 1–2 跳，就是毫秒级** —— **不需要任何额外组件**。

★★ **实现修正（`B127`，2026-09-19）—— 上表里的「递归 CTE」改为「逐层 BFS」**：
⚠ 递归 CTE 若要防环，必须携带**路径数组**（`path || node`）——
这会让中间行数按「**简单路径条数**」增长，在菱形依赖 / 中心节点上**指数爆炸**
（★ 爆的不是节点数，是**路径数** —— 这才是真正杀不死的问题）。
逐层 BFS 每层**只做一次索引扫描**，中间行数上限 = 该层 frontier 的相邻边数
⇒ ★ **O(V+E)，而非 O(路径数)**；且每层之间可检查预算 ⇒ **能优雅截断**（返回标志），
而不是被数据库杀掉。性能同量级（都是索引扫描），**安全性高一个量级**。

## G3 表结构与索引

```sql
-- 边表（★ 单向存一行，不存双向 —— 省一半空间）
CREATE TABLE graph_edge (
  project_ref  char(32)     NOT NULL,
  from_uid     varchar(512) NOT NULL,
  to_uid       varchar(512) NOT NULL,
  type         varchar(32)  NOT NULL,   -- calls / imports / defines / ...
  origin       varchar(16)  NOT NULL,   -- parsed / manual
  ...
);

-- ★★ 两个索引，一个都不能少
CREATE INDEX ON graph_edge (project_ref, from_uid, type);   -- 正向：我调用了谁
CREATE INDEX ON graph_edge (project_ref, to_uid,   type);   -- ★ 反向：谁调用了我
```

> ⚠ **反向索引最容易漏** —— ✖ 没有它，「**谁调用了我**」（**上游** —— 读代码时最常问的问题）就要**全表扫描**。

★ **邻接表 + 两个索引，就是"不上图库"的全部存储设计。**

## G3.5 ★★ 三层标识体系（2026-09-19 定稿 · `B117`）

| 标识 | 谁用 | 唯一性 | 可变性 |
|---|---|---|---|
| **`node_id`** | ★ **服务器内部**（主键 / 外键） | ★★★ **绝对唯一**（PG 自增发号） | 永不变 |
| **`vid`** | ★ **对外 + 锚点挂载** | ★★★ **绝对唯一** | 永不变 |
| **`uid`** | ★ **人读**（展示 / 定位 / 搜索） | ⚠ **允许偶发重复** | 永不变 |

★ **唯一性由「服务器发号」保证，不依赖 `uid` 是否重复**：

```sql
node_id  BIGINT GENERATED BY DEFAULT AS IDENTITY   -- ★ PG 保证唯一、并发安全
vid      = node_id（或 H(project_ref ‖ node_id) 做混淆）
```

⚠ **对旧设计的修正**：旧定稿为 `vid = sha256_16(project_ref + "\0" + uid)`

- ★ 该公式成立的前提是「**两端 bit-exact**」（浏览器与服务端各自算出同一值）；
- ★ **现在只有服务端解析 ⇒ 前提消失 ⇒ 改回「发号」**（旧文档 `B21` 本就推荐过发号方案）。

★ **锚点必须挂 `vid`**（`CodeAnchor`）—— ❌ **不得挂 `uid`**：
⚠ 否则 **uid 重复时，解释会挂到错的节点上**。

★ **手动新增节点走同一个发号** ⇒ 自动 / 手动**天然统一**，不会有两套唯一性逻辑。

## G5 缓存策略

```
Redis: key   = astrolabe:neigh:{project_ref}:r{rev}:{vid}:d{depth}:{dir}:{etags}
       value = zlib(JSON 数组式紧凑编码)
       TTL   = 30 天（⚠ 只负责回收内存，★ 失效靠 rev，不靠 TTL）
```

| 场景 | 处理 |
|---|---|
| 图**未修补**（★ **99% 的时间**） | 直接命中缓存 ✅ |
| **重新解析 / 维护者修补后** | ★ `GraphRevision.rev + 1` ⇒ 旧代际**立刻不可达**（**O(1)**，❌ **不删任何 key**） |
| ⚠ **不要做** | 精确失效（只失效受影响节点）—— **复杂度高、收益小，一期不做** |
| ⚠ **也不要** | `SCAN` / `KEYS` 全库删 key —— 会**阻塞 Redis 主线程**，键越多越慢 |

> ★ **前提**：`B103` 的「**图不可变**」是这套缓存能成立的根本原因 —— 换成普通可变图应用，缓存**很快会脏**。

### ★ 实现（`B128`，2026-09-19）

| 项 | 位置 / 取值 |
|---|---|
| 缓存层 | `app/graph/cache.py` 的 `CachedGraphReader`（★ **装饰器**，套在任意 `GraphReader` 外面） |
| ★ 为什么是装饰器 | 缓存是**读路径策略**，不是**存储实现** —— ★ 换 Neo4j 时缓存**不用重做** |
| ★ 权威 rev | `graph/models.py` 的 `GraphRevision`（**数据库**，❌ 不是 Redis） |
| ⚠ 为什么不在 Redis | Redis 重启会丢数据 ⇒ rev 若**回退**，旧缓存会被**当成新的** |
| ★ bump 时机 | `write_graph()` **事务内**（❌ 不是事务后）—— 否则存在「图新了、rev 还旧」的窗口 |
| 单值上限 | **256 KB**，超过**不缓存**（常查的是"难懂的那几个函数"，结果很小；大结果属长尾） |
| TTL | **30 天**（★ 只回收内存，**不是**失效手段） |
| 失效代价 | ★ **O(1)** —— 只改一个数字 |

★★ **两条正确性纪律**（实现里已强制）：

| # | 纪律 | 违反后果 |
|---|---|---|
| **1** | **`limits` 非空 ⇒ 绕过缓存** | 自定义预算结果不同，混进同一条缓存会**串味** |
| **2** | **key 用「生效后」的 `depth`**，且 uid **先归一化成 vid** | `depth=None` 与 `depth=1` 结果相同 ⇒ 不归一化会**重复缓存** |

★★ **「不卡死系统」的三道保险**：

| # | 保险 | 取值 |
|---|---|---|
| 1 | `socket_timeout` / `socket_connect_timeout` | 1s / 0.5s（⚠ 长连接不设超时 = 可能**永久挂住**） |
| 2 | ★ **熔断器** | 连续失败 3 次 ⇒ **冷却 10s 内直接跳过 Redis**（连尝试都不做） |
| 3 | 全部 Redis 操作**尽力而为** | 任何异常都**降级为「无缓存」**，❌ 不向用户报错 |

### ★ 节点访问热度（同批产出，热力图的数据源）

> ★ 用户洞察原话：**「用户经常访问的就是哪几个难懂的函数，其他几乎不会查邻接节点」**。

| 项 | 设计 |
|---|---|
| 存储 | Redis **ZSET**：`astrolabe:hot:{metric}:{project_ref}` |
| ★ 按什么计数 | ★★ **`uid`，❌ 不是 `vid`** —— `vid` 是发号（`B117`），**不保证跨次解析相同** ⇒ 按 vid 记则**重新解析一次热度全归零** |
| ⚠ 代价（诚实记录） | `uid` 允许重复 ⇒ 同名节点**合并计数**（对"热度"这个用途可接受，甚至更合理） |
| 记谁 | ★ **只记邻域查询的「起点」**（用户点开的节点），❌ 不记返回的每个节点（一次点击可能带出 3000 个 ⇒ 一记就失真） |
| 记在哪 | ★ 只在 `traversal.neighborhood()`（① Web 入口）—— 调试命令 / 内部诊断**不污染统计** |
| 指标通道 | `visit` ✅ / `notes` ⚠ 将来 / `comments` ⚠ 将来（最终热度 = **加权合成**） |
| ✅ **已实现**（`B129`） | 计数在 Redis 是**热数据，重启会丢** ⇒ ★ 已由 `graph/heat.py` + `manage.py heat_flush` 定期合并进数据库 |

### ★ 热度合并（Redis → 数据库，`B129`）

| 层 | 角色 |
|---|---|
| Redis ZSET | **增量缓冲**（每请求一次 `ZINCRBY`，极轻） |
| ★ `NodeHeat` 表 | **权威累计值**（`project_ref + metric + uid` 唯一） |

★★ **三个不能省的细节**（每个都对应一种真实的丢数据 / 算错）：

| # | 细节 | ❌ 不这么做会怎样 |
|---|---|---|
| **1** | ★ **用 `RENAME` 原子轮换**，不是「读完再清零」 | 读完之后、清零之前进来的访问会被**一起减掉** ⇒ **丢计数** |
| **2** | ★ **残留批次要捡回来**（扫 `:flush:*`） | 轮换后、合并前崩了 ⇒ 那批计数**永远躺在临时 key 里** |
| **3** | ★ **幂等闸门 `HeatFlush`** | 写库后、删 key 前崩了 ⇒ 重跑**重复累加** ⇒ 热度虚高，越重启越离谱 |

> ★ `RENAME` 之所以对：它**原子** —— 轮换那一刻之后的所有 `ZINCRBY`
> 都落到**新的主 key**，❌ 不会被这次合并碰到 ⇒ **既不丢、也不重**。
>
> ★ **写库与「记录已处理」在同一个事务**（`HeatFlush` + `NodeHeat` 同事务）
> ⇒ 不存在"改了一半"的中间态。
>
> ⚠ **按 `uid` 存热度 → 节点被删后行**不删**（历史热度仍有价值），展示时与当前图 join 即可。
>
> ★ **读路径**（`heat.top_nodes`）= **DB 权威值 + Redis 未合并增量** ——
> 只读 DB 会"慢半拍"（刚点的还没落库），只读 Redis 会"丢历史"（重启就没）。

## G6 ★★ 算法接口（图语义定义 —— **将来可换图库的唯一预留点**）

**原则**：★ **接口按「图语义」定义，不按实现定义。**

```
✅ 正确的接口签名（一期 PG 实现；将来 Neo4j / Nebula 实现都能对得上）
   neighborhood(project_ref, uid, depth, direction)        -> {nodes, edges}
   shortest_path(project_ref, from_uid, to_uid, max_len)   -> [uid, ...]
   find_cycles(project_ref, max_len)                       -> [[uid, ...], ...]
   clusters(project_ref)                                    -> [{cluster_id, uids}]
   impact(project_ref, uid, direction)                      -> {nodes, edges}

❌ 禁止出现在接口上（会把 PG 泄露出去，将来换不掉）
   run_sql(...) / raw_query(...) -> cursor / 表名 / SQL 片段
```

★ **判据**：**参数与返回值里不能出现任何 PG 特有的东西**（SQL / cursor / 表名）。

### ⚠ 抽象的分寸

| 做法 | 评价 |
|---|---|
| ❌ 现在就建 **抽象层 / 工厂 / 适配器** | ⚠ **过度设计**（连第一个实现都还没有） |
| ✅ **只定「接口 + 一个实现」（PG 版）** | ★ **正确** —— 一个接口 + 一个实现**不叫抽象层**，叫**正常的模块边界** |
| ★★ **位置与形状现在定** | ✅ 现在定**几乎免费**；三个月后定要**重写** |
